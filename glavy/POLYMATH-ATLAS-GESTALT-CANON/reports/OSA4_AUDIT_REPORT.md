## 1. МЕТОДОЛОГИЯ

### 1.1. Что в этом отчёте значит «проверено»

Аудит формальной системы может означать три разные вещи, и их важно не
смешивать:

1. **Синтаксическая проверка.**  Все объявления существуют, имена
   разрешаются, типы согласованы.  Это делает компилятор Lean при сборке.
2. **Доказательная проверка.**  Каждое заявленное свойство сопровождается
   доказательством, принятым ядром Lean, без `sorry` и без пользовательских
   аксиом.  Это основной режим настоящего аудита.
3. **Эмпирическая адекватность.**  Соответствие формальной модели реальному
   поведению системы.  Здесь **не** утверждается: формализована
   спецификация, а не измеренная система (см. §12 «Ограничения»).

Всякий раз, когда ниже написано «доказано», имеется в виду пункт 2, и рядом
указано имя теоремы, которое можно проверить командой
`#print axioms <имя>`.

### 1.2. Что значит «непротиворечивость» здесь

Формально «непротиворечивость набора аксиом» — это существование модели.
В настоящем проекте законы LAW-001 – LAW-018 **не являются аксиомами**: это
утверждения о конкретной, явно построенной структуре (типы `TypeLattice`,
`KState`, `Op`, `World`, `Step`, `Belief`, `EffectLevel`).  Все 18 из них
доказаны:

```lean
theorem lawbook_holds : ∀ l : LawId, l.holds
```

Отсюда непротиворечивость следует немедленно и в сильной форме: у конъюнкции
всех законов есть модель — та самая, в которой они доказаны.  Формально это
записано так:

```lean
theorem lawbook_consistent :
    (∀ l : LawId, l.holds) ∧ ¬ ((∀ l : LawId, l.holds) → False)
```

Первый конъюнкт — существование модели, второй — невозможность вывести из
законов ложь (в предположении непротиворечивости самого Lean, то есть теории
CIC с тремя стандартными аксиомами).

Важная оговорка: непротиворечивость **сама по себе** ничего не стоит, если
законы вырождены — например, если их посылки невыполнимы.  Поэтому доказана
и невырожденность (§3.3).

### 1.3. Что значит «тест пройден»

Тест Torture Set — это не отметка и не запуск скрипта, а **утверждение**
`TortureId.passed t` о поведении ядра.  «Пройден» означает, что это
утверждение доказано.  Для вычислимых сценариев доказательство —
вычисление ядром Lean (`decide`), то есть вердикт компилятора композиций
*вычислен*, а не заявлен.

Отдельно подчеркнём: **отрицательный результат тоже может быть пройденным
тестом**.  Тест T18 фиксирует, что обратная импликация LAW-011 ложна; он
пройден, потому что доказано именно это.  Проваленным тест считался бы, если
бы ожидаемое поведение не удалось доказать или было бы опровергнуто.

## 2. РЕЕСТР ЗАКОНОВ: ПОСТАТЕЙНЫЙ РАЗБОР

В этом разделе для каждого закона приведены: формулировка кодекса, точная
формула из `LawId.holds` (файл `RequestProject/OSA4/Lawbook.lean`), имя
доказательства, свидетели и замечания аудита.

Общая теорема раздела:

```lean
theorem lawbook_holds : ∀ l : LawId, l.holds
theorem lawbook_card : Fintype.card LawId = 18
```

### 2.1. LAW-001 — Type Reflexivity

*Кодекс:* всякий тип является своим подтипом, `∀ A ∈ T, A ⊑ A`.

*Формула:*

```lean
| .LAW_001 => ∀ (L : TypeLattice) (a : TypeTag), L.IsSubtype a a
```

*Доказательство:* `TypeLattice.isSubtype_refl` — непосредственно из
определения `IsSubtype := Relation.ReflTransGen Edge`.

*Свидетели:* `basis_law001_boundary` — рефлексивность работает и для метки,
не объявленной ни в одном ребре решётки (граничный случай: замыкание не
требует присутствия метки в таблице).

*Замечание аудита:* закон тривиален по построению и потому не несёт
информации о конкретной решётке; содержательная часть системы типов — в
LAW-002 и в антисимметрии (§5).

*Статус:* ✅ доказан.

### 2.2. LAW-002 — Type Transitivity

*Кодекс:* `A ⊑ B ∧ B ⊑ C ⇒ A ⊑ C`.

*Формула:*

```lean
| .LAW_002 => ∀ (L : TypeLattice) (a b c : TypeTag),
    L.IsSubtype a b → L.IsSubtype b c → L.IsSubtype a c
```

*Доказательство:* `TypeLattice.isSubtype_trans`.

*Свидетели:* `basis_law002_positive` — цепочка
`CalibratedValue ⊑ MeasuredValue ⊑ Datum` замыкается до
`CalibratedValue ⊑ Datum`; `basis_law002_negative` — в пустой решётке
выводится только равенство (`isSubtype_empty_iff`), то есть транзитивное
замыкание ничего не «додумывает».

*Замечание аудита:* монотонность по расширению решётки доказана
(`isSubtype_mono`): добавление объявлений не отменяет уже выведенных
отношений.  Это важно для эволюции онтологии: расширение словаря типов —
консервативная операция.

*Статус:* ✅ доказан.

### 2.3. LAW-003 — State Conservation

*Кодекс:* оператор не меняет того, чего не касается.

*Формула:*

```lean
| .LAW_003 => ∀ (o : Op) (s : KState),
    (∀ f : FactId, f ∉ o.kill → f ∉ o.produces →
      (o.exec s).factStatus f = s.factStatus f) ∧
    (∀ v : VarName, v ∉ o.modifies → (o.exec s).varValue v = s.varValue v)
```

*Доказательство:* `factStatus_exec_untouched`, `varValue_exec_untouched`.

*Свидетели:* `basis_law003_positive` (нетронутый факт сохраняет статус),
`basis_law003_negative` (затронутый — меняет; закон говорит именно о
нетронутых), `basis_law003_boundary`.

*Замечание аудита:* аналог закона для оси E (пространства идентичностей)
кодексом не был выписан; он добавлен аудитом и доказан:

```lean
theorem step_frame (w : World) (st : Step) {j : ObjId} (h : j ≠ st.touches) :
    (Step.apply w st).phaseOf j = w.phaseOf j
```

где `Step.touches` — объект, которого касается шаг.  Это ключ к ответу на
критический вопрос 1 (§9.1).

*Статус:* ✅ доказан.

### 2.4. LAW-004 — No Resurrection

*Кодекс:* уничтоженный объект не возвращается к жизни под тем же
идентификатором.

*Формула:*

```lean
| .LAW_004 => ∀ (w : World) (st : Step) (i : ObjId),
    Step.legal w st = true → w.phaseOf i = some .Destroyed →
      (Step.apply w st).phaseOf i ≠ some .Available
```

*Доказательство:* `law004_no_resurrection` — разбор всех пяти видов шага.
Шаг `.resurrect` недопустим по контракту (`law004_resurrect_illegal`), а
остальные либо не касаются объекта `i`, либо переводят его не в `Available`.

*Свидетели:* `torture_T04a_resurrection_rejected` (отрицательный),
`torture_T04b_recreation_legal` (положительный: воссоздание допустимо),
`torture_T04_separation` (оба на одном и том же состоянии).

*Замечание аудита:* закон непуст — существует мир с уничтоженным объектом и
допустимым шагом (`lawbook_hypotheses_satisfiable`, первый конъюнкт).

*Статус:* ✅ доказан.

### 2.5. LAW-005 — Consume Safety

*Кодекс:* потребление допустимо ровно тогда, когда ресурс доступен.

*Формула:*

```lean
| .LAW_005 => ∀ (w : World) (i : ObjId),
    Step.legal w (.consume i) = true ↔ w.phaseOf i = some .Available
```

*Доказательство:* `law005_consume_iff_available`.

*Свидетели:* `torture_T12_double_consume` (второе потребление недопустимо),
`T12_double_consume` (тот же вердикт вычислен компилятором:
`REJECT / E_INVARIANT_VIOLATION`).

*Замечание аудита:* это единственный закон, сформулированный как
равносильность, и она действительно двусторонняя — в отличие от LAW-011
(§9.3).  Обе стороны выделены в отдельные леммы
(`consume_requires_available`, `consume_legal_of_available`), плюс
контрапозиция (`consume_illegal_of_not_available`).

*Статус:* ✅ доказан.

### 2.6. LAW-006 — Destroy / Predicate Liveness Safety

*Кодекс:* `KILL(X)` допустим только при `X ∉ LIVE_OUT`; уничтожение факта
делает его недоказанным.

*Формула:*

```lean
| .LAW_006 => ∀ (o : Op) (s : KState) (f : FactId),
    f ∈ o.kill → f ∉ o.produces →
      eval (o.exec s) (.factExists f) ≠ .TRUE_KNOWN
```

*Доказательство:* `law006_kill_live_fact` через `factStatus_exec_kill`.

*Свидетели:* `T02_pass` (уничтожение X не мешает анализу Y),
`T03_liveness_violation` (`REJECT / E_LIVENESS_VIOLATION`),
`T11_invalidate_live` (инвалидация живого предиката).

*Замечание аудита:* «безопасная сторона» закона тоже доказана
(`live_preserved_of_untouched`): если оператор не трогает нужный факт, тот
переживает исполнение.  Вместе с LAW-006 это даёт точную характеризацию.

*Статус:* ✅ доказан.

### 2.7. LAW-007 — Liveness Soundness

*Кодекс:* композиция с вердиктом PASS не содержит нарушений живучести.

*Формула:*

```lean
| .LAW_007 => ∀ sc : Scenario,
    (compile sc).verdict = .PASS → livenessViolation sc.goal sc.chain = none
```

*Доказательство:* `pass_no_liveness_violation`.

*Свидетели:* `T01_fixed_pass` (положительный), `T05_undecidable`
(граничный), `basis_law007_negative`, `basis_law007_repair`.

*Замечание аудита:* закон — часть моста Bridge 4 (§6.4): вердикт компилятора
влечёт операционное содержание законов, а не наоборот.

*Статус:* ✅ доказан.

### 2.8. LAW-008 — Effect Monotonicity / Effect Monoid

*Кодекс:* суммарный эффект не зависит от группировки операторов.

*Формула:*

```lean
| .LAW_008 => ∀ l₁ l₂ : List EffectLevel,
    EffectLevel.aggregate (l₁ ++ l₂) =
      EffectLevel.join (EffectLevel.aggregate l₁) (EffectLevel.aggregate l₂)
```

*Доказательство:* `EffectLevel.aggregate_append`.

*Свидетели:* `basis_law008_positive/negative/boundary/branch`, а также
добавленные аудитом `aggregate_insert_unit`, `aggregate_filter_unit`,
`rank_aggregate_eq_max`.

*Замечание аудита:* к закону добавлены единица и её свойства (§7).  Кроме
того, доказано, что политика эффектов проверяется пооперационно
(`EffectPolicy.allows_iff`): агрегация не может «спрятать» запрещённый
эффект внутри длинной цепочки.

*Статус:* ✅ доказан.

### 2.9. LAW-009 — Epistemic Non-Overclaim

*Кодекс:* без явно порождённого свидетельства неопределённость не
уменьшается; уверенность нельзя «отмыть» композицией.

*Формула:*

```lean
| .LAW_009 => ∀ (l : List UStep) (a : UStep), UChain (a :: l) →
    (∀ s ∈ a :: l, s.honest) → (∀ s ∈ a :: l, s.evidence = false) →
      a.uIn ≤ (List.getLast (a :: l) (by simp)).uOut
```

*Доказательство:* `law009_no_overclaim` (индукция по цепочке).

*Свидетели:* `uncertainty_drop_needs_evidence` (снижение неопределённости без
свидетельства делает шаг нечестным), `basis_law009_positive/boundary`.

*Замечание аудита:* формулировка требует согласованности цепочки
(`UChain`) — выход каждого шага является входом следующего.  Без этого
условия закон был бы ложен, и это правильно: «неопределённость на входе»
нельзя сравнивать с выходом несвязанного шага.

*Статус:* ✅ доказан.

### 2.10. LAW-010 — Composition Soundness

*Кодекс:* композиция `A ; B` допустима ровно тогда, когда существует
промежуточное состояние, в котором выполнены предусловия `B`.

*Формула:*

```lean
| .LAW_010 => ∀ (a b : Op) (s : KState),
    (a.enabled s ∧ b.enabled (a.exec s)) ↔
      ∃ s' : KState, a.enabled s ∧ s' = a.exec s ∧ b.enabled s'
```

*Доказательство:* `law010_composition_sound`.

*Свидетели:* `basis_law010_positive/negative`.

*Замечание аудита:* закон выражает детерминированность исполнения:
«существует промежуточное состояние» в детерминированном ядре означает «это
состояние ровно одно, и оно равно `exec A s`».  При переходе к
недетерминированной семантике формулировку придётся пересматривать; это
зафиксировано как ограничение (§12).

*Статус:* ✅ доказан.

### 2.11. LAW-011 — Effect Authorization Soundness

*Кодекс:* `Exec(Op,S) ⇒ Authorized(S,Op)`.

*Формула:*

```lean
| .LAW_011 => ∀ (s : KState) (o : Op), execAllowed s o → authStatus s o = .TRUE_KNOWN
```

*Доказательство:* `law011_exec_implies_authorized`.

*Свидетели:* `T13_missing_authorization` (REPAIR при отсутствии токена и
наличии авторизатора), `T13_repaired_pass`, `T13_auth_denied_reject`
(доказанный отказ даёт REJECT, а не REPAIR), `basis_law011_boundary`.

*Замечание аудита:* **это одна из двух находок.**  Двусторонняя форма закона
некорректна: авторизация необходима, но не достаточна.  Подробно — §9.3.

*Статус:* ✅ доказан в односторонней форме; двусторонняя опровергнута.

### 2.12. LAW-012 — Predicate Transformer (WP) Soundness

*Кодекс:* `{WP(Op,Q)} Op {Q}`.

*Формула:*

```lean
| .LAW_012 => ∀ (o : Op) (s : KState) (q : Pred),
    eval s (wp o q) = .TRUE_KNOWN → eval (o.exec s) q = .TRUE_KNOWN
```

*Доказательство:* `law012_wp_sound` как следствие точной характеризации
`eval_exec_eq_eval_wp : eval (o.exec s) q = eval s (wp o q)`.

*Свидетели:* `law012_wp_complete` (полнота, то есть `WP` действительно
слабейшее предусловие), `wp_comp` (композиция), `basis_law012_*`.

*Замечание аудита:* равенство `eval (exec o s) q = eval s (wp o q)` сильнее
закона: оно даёт и корректность, и полноту, и потому позволяет переносить
любой вердикт через исполнение в обе стороны.  Это используется в Bridge 4.

*Статус:* ✅ доказан.

### 2.13. LAW-013 — Join Commutativity

*Формула:* `∀ a b : Belief, Belief.join a b = Belief.join b a`.

*Доказательство:* `Belief.join_comm`.

*Свидетели:* `torture_T09_conflict` (`TRUE ⊔ FALSE = CONFLICT`),
`basis_law013_positive`.

*Замечание аудита:* коммутативность выполняется и для напечатанной таблицы,
и для исправленной алгебры; расхождение таблиц касается только
ассоциативности (LAW-014).

*Статус:* ✅ доказан.

### 2.14. LAW-014 — Join Associativity

*Формула:*
`∀ a b c : Belief, join (join a b) c = join a (join b c)`.

*Доказательство:* `Belief.join_assoc`.

*Замечание аудита (важное, унаследованное):* для **напечатанной**
пятизначной таблицы слияния ассоциативность **не выполняется**:

```lean
theorem law014_fails_for_printed_table :
    (¬ ∀ x y z : EV, joinSpec (joinSpec x y) z = joinSpec x (joinSpec y z)) ∧
    LawId.LAW_014.holds
```

Закон доказан для исправленной алгебры свидетельств `Belief`, которая
сохраняет все вердикты Torture Set; расхождение локализовано и доказано
(`spec_disagreement_eq`).  Настоящий аудит подтверждает эту поправку и не
находит новых расхождений.

*Статус:* ✅ доказан для `Belief`; ❌ для напечатанной таблицы (расхождение
задокументировано и доказано).

### 2.15. LAW-015 — Join Idempotence

*Формула:* `∀ a : Belief, Belief.join a a = a`.

*Доказательство:* `Belief.join_idem`.

*Свидетели:* `joinList_duplicate` — повторение одного и того же свидетельства
не усиливает вывод (защита от «эхо-камеры»: дублирование источника не
увеличивает уверенность).

*Статус:* ✅ доказан.

### 2.16. LAW-016 — Recreation Identity

*Кодекс:* воссоздание порождает объект с **новым** идентификатором.

*Формула:*

```lean
| .LAW_016 => ∀ (w : World) (old new : ObjId),
    Step.legal w (.recreate old new) = true → new ≠ old
```

*Доказательство:* `law016_recreate_new_id`.

*Свидетели:* `recreate_provenance` (новый объект доступен и несёт провенанс),
`recreate_keeps_old_destroyed` (предшественник остаётся уничтоженным),
`basis_law016_negative/boundary`.

*Замечание аудита:* закон дополнен требованием свежести идентификатора
(`recreate_requires_fresh`) и требованием фазы `Destroyed`
(`recreate_requires_destroyed`) — оба следуют из контракта `Step.legal`, но
в кодексе явно не выписаны (§8.2).

*Статус:* ✅ доказан.

### 2.17. LAW-017 — Predicate Invalidation Soundness

*Кодекс:* `Invalidates(P) ≠ proves ¬P`.

*Формула:*

```lean
| .LAW_017 => ∀ (o : Op) (s : KState) (f : FactId),
    f ∈ o.kill → f ∉ o.produces →
      eval (o.exec s) (.pnot (.factExists f)) ≠ .TRUE_KNOWN
```

*Доказательство:* `law017_invalidate_not_refute`.

*Свидетели:* `basis_law017_positive`, `consume_X_kills`.

*Замечание аудита:* закон совместен с LAW-006 именно потому, что семантика
четырёхзначна (§9.2).

*Статус:* ✅ доказан.

### 2.18. LAW-018 — Repair Soundness

*Кодекс:* среди корректных планов ремонта оптимизатор выбирает
лексикографически наилучший, и выбранный план корректен.

*Формула:*

```lean
| .LAW_018 => ∀ (s : KState) (goal : Pred) (plans : List RepairPlan),
    (∀ p ∈ plans, p.sound s goal) → ∀ v : RVec,
      RVec.best (plans.map RepairPlan.vec) = some v →
        ∃ p ∈ plans, p.vec = v ∧ p.sound s goal ∧ ∀ q ∈ plans, RVec.le v q.vec
```

*Доказательство:* `law018_repair_sound`.

*Свидетели:* `torture_T15_safe_beats_cheap` (безопасность доминирует над
стоимостью), `basis_law018_negative`.

*Замечание аудита:* закон говорит о **выборе** среди данных планов и ничего
не говорит о **полноте** их порождения.  Именно этот зазор и вскрыт
критическим вопросом 4 (§9.4): вердикт `REPAIR` компилятора опирается на
более слабый критерий, чем корректность плана.

*Статус:* ✅ доказан.

## 3. НЕПРОТИВОРЕЧИВОСТЬ СВОДА ЗАКОНОВ

### 3.1. Совместная выполнимость

Главный результат раздела:

```lean
theorem lawbook_consistent :
    (∀ l : LawId, l.holds) ∧ ¬ ((∀ l : LawId, l.holds) → False)
```

Все восемнадцать законов выполнены **одновременно** в одной и той же
структуре.  Это сильнее попарной совместимости и сильнее «нет известных
контрпримеров»: контрпримеров не может быть в принципе, поскольку каждое
утверждение доказано.

Попарная и произвольно-подмножественная совместимость выводятся сразу:

```lean
theorem lawbook_pairwise_consistent (l₁ l₂ : LawId) : l₁.holds ∧ l₂.holds
theorem lawbook_subset_consistent (S : LawId → Prop) : ∀ l, S l → l.holds
```

Первое покрывает все 18 × 18 = 324 упорядоченные пары (в том числе обе пары,
названные в критических вопросах), второе — все 2¹⁸ = 262 144 подмножества.
Ни одно из них не требуется проверять по отдельности: утверждение доказано
для произвольного `S`.

### 3.2. Почему конъюнкция законов не тривиальна

Конъюнкция истинных утверждений всегда непротиворечива, поэтому сам факт
доказуемости мог бы оказаться дешёвым: например, если бы законы были
записаны так, что их посылки невыполнимы («если 0 = 1, то …»).  Аудит
проверяет, что это не так.

### 3.3. Невырожденность: посылки законов выполнимы

```lean
theorem lawbook_hypotheses_satisfiable :
    (∃ (w : World) (st : Step) (i : ObjId),
      Step.legal w st = true ∧ w.phaseOf i = some .Destroyed) ∧
    (∃ (w : World) (i : ObjId), Step.legal w (.consume i) = true) ∧
    (∃ (o : Op) (f : FactId), f ∈ o.kill ∧ f ∉ o.produces) ∧
    (∃ (s : KState) (o : Op), execAllowed s o) ∧
    (∃ (o : Op) (s : KState) (q : Pred), eval s (wp o q) = .TRUE_KNOWN) ∧
    (∃ (w : World) (old new : ObjId), Step.legal w (.recreate old new) = true)
```

Конъюнкт за конъюнктом:

| закон | посылка | свидетель |
|-------|---------|-----------|
| LAW-004 | существует допустимый шаг при уничтоженном объекте | мир `[⟨1, Destroyed, []⟩]`, шаг `recreate 1 2` |
| LAW-005 | существует допустимое потребление | мир `[⟨1, Available, []⟩]`, шаг `consume 1` |
| LAW-006 / LAW-017 | существует оператор, уничтожающий факт | `CONSUME_X`, факт `"X"` |
| LAW-011 | существует разрешённое исполнение | состояние `[("X", TRUE_KNOWN)]`, оператор `ANALYZE_X` |
| LAW-012 | существует доказанное WP-предусловие | `CREATE_X`, цель `factExists "X"` |
| LAW-016 | существует допустимое воссоздание | мир `[⟨1, Destroyed, []⟩]`, шаг `recreate 1 2` |

Все шесть свидетелей вычислены (`decide`).  Таким образом законы не
выполняются «вхолостую»: каждый из них в каких-то состояниях действительно
что-то запрещает или гарантирует.

### 3.4. Отдельно: где именно спецификация всё же расходится сама с собой

Единственное известное расхождение — напечатанная пятизначная таблица
слияния свидетельств против LAW-014.  Оно не «замазано», а доказано:

```lean
theorem joinSpec_not_assoc :
    ¬ ∀ x y z : EV, joinSpec (joinSpec x y) z = joinSpec x (joinSpec y z)
```

и локализовано (`spec_disagreement_eq` перечисляет точки расхождения
исправленной алгебры с таблицей).  Настоящий аудит подтверждает: других
расхождений между законами и ядром не обнаружено, и вердикты Torture Set при
переходе к исправленной алгебре сохраняются (T08, T09, T10 — §11).

## 4. ГРАФ ЗАВИСИМОСТЕЙ ЗАКОНОВ

### 4.1. Постановка

«Циклическая зависимость» в системе законов опасна тем, что обоснование
закона может неявно опираться на него самого.  В настоящем проекте такой
риск в принципе ограничен: каждый закон доказан из конструкции ядра, а не из
других законов.  Тем не менее содержательная зависимость (какое понятие
осмысленно только вместе с каким) существует, и аудит фиксирует её явно —
как данные, которые можно проверить.

### 4.2. Данные

```lean
def LawId.dependsOn : LawId → List LawId
  | .LAW_007 => [.LAW_006]
  | .LAW_010 => [.LAW_012]
  | .LAW_011 => [.LAW_008]
  | .LAW_016 => [.LAW_004]
  | .LAW_017 => [.LAW_006]
  | .LAW_018 => [.LAW_010, .LAW_012]
  | _        => []
```

Чтение таблицы:

| закон | опирается на | почему |
|-------|--------------|--------|
| LAW-007 Liveness Soundness | LAW-006 | «нарушение живучести» определено уничтожением живого факта |
| LAW-010 Composition Soundness | LAW-012 | композиция описана через предусловия/WP |
| LAW-011 Authorization | LAW-008 | требование авторизации задаётся уровнем эффекта |
| LAW-016 Recreation Identity | LAW-004 | воссоздание имеет смысл лишь при запрете воскрешения |
| LAW-017 Invalidation | LAW-006 | уточняет ту же операцию `kill` |
| LAW-018 Repair Soundness | LAW-010, LAW-012 | план ремонта оценивается исполнением цепочки |

### 4.3. Слои и ацикличность

```lean
def LawId.layer : LawId → ℕ   -- 0 для базовых, 1 для производных, 2 для LAW-018

theorem lawDeps_layer_lt : ∀ (l d : LawId), d ∈ l.dependsOn → d.layer < l.layer
theorem lawDeps_acyclic (l : LawId) : ¬ Relation.TransGen LawDepends l l
theorem lawDeps_irrefl : ∀ l : LawId, l ∉ l.dependsOn
```

`lawDeps_layer_lt` проверено исчерпывающим перебором всех 18 законов и всех
их зависимостей (`decide`).  Из строгого возрастания слоя вдоль ребра
следует строгое возрастание вдоль любого пути (`layer_lt_of_transGen`), а
значит цикла нет ни на каком расстоянии.

Распределение по слоям:

| слой | законы | число |
|------|--------|-------|
| 0 | LAW-001, 002, 003, 004, 005, 006, 008, 009, 012, 013, 014, 015 | 12 |
| 1 | LAW-007, 010, 011, 016, 017 | 5 |
| 2 | LAW-018 | 1 |

Максимальная глубина зависимости — 2 (LAW-018 → LAW-010 → LAW-012).

### 4.4. Что этот результат не утверждает

Граф зафиксирован аудитом как **данные о структуре обоснований**, а не
выведен автоматически из текстов доказательств.  Утверждение, которое
проверено машиной, — именно ацикличность этого графа и согласованность его со
слоями.  Если бы кто-то захотел добавить ребро, создающее цикл,
`lawDeps_layer_lt` перестал бы проходить `decide`, то есть проверка не
пропустила бы такое изменение.

## 5. СИСТЕМА ТИПОВ (ОСЬ D)

### 5.1. Запрос и краткий ответ

Запрошено: «проверь antisymmetry: `IsSubtype a b → IsSubtype b a → a = b`».

Ответ: в общем виде утверждение **ложно**, и это доказано.  Оно становится
истинным при явном дополнительном условии — отсутствии циклов в объявленной
таблице подтипов, — которое формализовано как существование градуировки.
Рабочая решётка кодекса этому условию удовлетворяет.

### 5.2. Почему антисимметрия не следует из LAW-001/002

`IsSubtype` определена как рефлексивно-транзитивное замыкание объявленных
рёбер:

```lean
def IsSubtype : TypeTag → TypeTag → Prop := Relation.ReflTransGen L.Edge
```

Замыкание не «знает», что объявления не должны образовывать циклов.  Если
инженер объявил `A ⊑ B` и `B ⊑ A`, оба отношения выводятся, но `A ≠ B`:

```lean
def cyclicLattice : TypeLattice := ⟨[("A", "B"), ("B", "A")]⟩

theorem cyclicLattice_both :
    cyclicLattice.IsSubtype "A" "B" ∧ cyclicLattice.IsSubtype "B" "A"

theorem isSubtype_not_antisymmetric :
    ¬ ∀ (L : TypeLattice) (a b : TypeTag),
        L.IsSubtype a b → L.IsSubtype b a → a = b
```

Это не дефект доказательства, а дефект формулировки: антисимметрия — не
свойство отношения `IsSubtype` как такового, а **условие корректности
конкретной таблицы типов**.

### 5.3. Точная граница

Достаточное условие:

```lean
def Graded (L : TypeLattice) (r : TypeTag → ℕ) : Prop := ∀ p ∈ L.edges, r p.1 < r p.2

theorem antisymmetric_of_graded {L r} (hg : Graded L r) : L.Antisymmetric
```

Доказательство опирается на две леммы:

* `rank_le_of_isSubtype` — вдоль подтипизации ранг не убывает (индукция по
  замыканию);
* `rank_lt_of_isSubtype_of_ne` — для различных меток ранг возрастает строго
  (разбор первого шага пути: `Relation.ReflTransGen.cases_head`).

Необходимое условие (частичное) тоже доказано:

```lean
theorem no_two_cycle_of_antisymmetric (h : L.Antisymmetric)
    (hab : L.Edge a b) (hba : L.Edge b a) : a = b
```

а контрпример показан не-градуированным:

```lean
theorem cyclicLattice_not_graded : ¬ ∃ r, TypeLattice.Graded cyclicLattice r
```

Таким образом «градуирована» и «антисимметрична» разделяют один и тот же
содержательный смысл: отсутствие нетривиальных циклов в объявлениях.

### 5.4. Валидация рабочей решётки

```lean
def demoLattice : TypeLattice :=
  ⟨[("CalibratedValue", "MeasuredValue"), ("MeasuredValue", "Datum")]⟩

def demoRank (t : TypeTag) : ℕ :=
  if t = "CalibratedValue" then 0 else if t = "MeasuredValue" then 1
  else if t = "Datum" then 2 else 3

theorem demoLattice_graded : TypeLattice.Graded demoLattice demoRank
theorem demoLattice_antisymmetric : demoLattice.Antisymmetric
```

Проверки цепочки:

| утверждение | статус | теорема |
|-------------|--------|---------|
| `CalibratedValue ⊑ MeasuredValue` | ✅ | `demoLattice_chain.1` |
| `MeasuredValue ⊑ Datum` | ✅ | `demoLattice_chain.2.1` |
| `CalibratedValue ⊑ Datum` (транзитивно) | ✅ | `basis_law002_positive` |
| `Datum ⊑ CalibratedValue` | ❌ (и это правильно) | `demoLattice_no_reverse.1` |
| `MeasuredValue ⊑ CalibratedValue` | ❌ | `demoLattice_no_reverse.2.1` |
| `Datum ⊑ MeasuredValue` | ❌ | `demoLattice_no_reverse.2.2` |
| `Unheard ⊑ Unheard` | ✅ | `demoLattice_unheard.1` |
| `Unheard ⊑ Datum` | ❌ | `demoLattice_unheard.2` |
| антисимметрия решётки | ✅ | `demoLattice_antisymmetric` |

Последние две строки существенны: незнакомая метка сравнима только с собой,
то есть решётка не «додумывает» подтипизацию для типов, о которых ничего не
объявлено.  Это ровно то поведение, которого требует эпистемическая
дисциплина ядра (`UNKNOWN ≠ FALSE`).

### 5.5. Рекомендация

Условие градуированности следует сделать частью контракта конфигурации:
любая поставляемая таблица типов должна сопровождаться функцией ранга (или
проверкой ацикличности), иначе антисимметрия не гарантирована.  В терминах
проекта: рядом с `TypeLattice` держать доказательство `Graded`.

## 6. МОСТЫ МЕЖДУ СЛОЯМИ (BRIDGE 1 – BRIDGE 4)

### 6.0. Что здесь называется мостом

Ядро OSA-4.0 состоит из четырёх слоёв, определённых независимо:

1. **Система типов** — ось D: метки типов и объявленная подтипизация.
2. **Пространство идентичностей** — ось E: объекты, фазы жизненного цикла,
   шаги `create / consume / destroy / recreate`.
3. **Семантическое ядро** — состояние `KState`, предикаты `Pred`,
   четырёхзначная семантика `PT`, операторы `Op` и трансформер `wp`.
4. **Компилятор и законы** — вердикт `compile` и свод LAW-001 – LAW-018.

Слои связаны только через понятия, которые в них называются одинаково.
«Мост» — доказанное утверждение о том, что это совпадение имён не случайно:
существует перевод понятий одного слоя в другой, и перевод сохраняет
существенные свойства.  Без мостов формализация распадается на четыре
независимые теории, каждая из которых по-своему верна, но ни одна не
говорит о системе в целом.

Итог раздела:

```lean
theorem bridges_valid : (Bridge 1) ∧ (Bridge 2) ∧ (Bridge 3) ∧ (Bridge 4)
```

### 6.1. Bridge 1 — типы ↔ артефакты

**Что связывает.** Отношение подтипизации (ось D) и пространство артефактов
(произведение пяти осей).

**Перевод.**

```lean
def ArtifactType.SubstitutableFor (L : TypeLattice) (a b : ArtifactType) : Prop :=
  L.IsSubtype a.typeTag b.typeTag ∧ a.category = b.category ∧ a.role = b.role ∧
    a.level = b.level ∧ a.phase = b.phase
```

Артефакт подставим вместо другого, если он занимает ту же позицию по осям
A, B, C, E, а его тип — подтип требуемого.

**Что доказано.**

| свойство | теорема |
|----------|---------|
| рефлексивность (перевод LAW-001) | `ArtifactType.substitutableFor_refl` |
| транзитивность (перевод LAW-002) | `ArtifactType.substitutableFor_trans` |
| антисимметрия в градуированной решётке | `ArtifactType.substitutableFor_antisymm` |
| подъём подтипизации на артефакты | `bridge1_type_artifact` (третий конъюнкт) |

**Почему это содержательно.**  Ортогональность осей (§3 кодекса) означает,
что тип не определяет уровень, роль или фазу.  Мост показывает, что при
этом подтипизация всё же поднимается до отношения на артефактах — но только
«вдоль оси D», не смешивая оси.  Иначе говоря, подстановка по типу законна
лишь при совпадении остальных координат; это исключает молчаливую подмену
артефакта уровня L1 артефактом уровня L3 «потому что типы совместимы».

**Статус:** ✅.

### 6.2. Bridge 2 — ядро ↔ эффекты и авторизация

**Что связывает.** Исполнение операторов (`execAllowed`, `chainEnabled`) и
алгебру эффектов с авторизацией.

**Что доказано.**

```lean
theorem chainEnabled_authorized :
    ∀ (ops : List Op) (s : KState), chainEnabled ops s →
      ∀ o ∈ ops, ∃ st : KState, execAllowed st o ∧ authStatus st o = .TRUE_KNOWN

theorem chainEffects_policy_iff (p : EffectPolicy) (ops : List Op) :
    p.allows (chainEffects ops) = true ↔ ∀ o ∈ ops, o.effect.rank ≤ p.maxLevel.rank

theorem chainEffects_append (l₁ l₂ : List Op) :
    aggregate (chainEffects (l₁ ++ l₂)) =
      join (aggregate (chainEffects l₁)) (aggregate (chainEffects l₂))
```

и, как третий конъюнкт `bridge2_kernel_effects`, невозможность исполнения
без токена (`no_exec_without_token`).

**Как читать.**

* Первое утверждение — LAW-011 вдоль всей цепочки: если цепочка исполнима
  шаг за шагом, то у каждого её оператора есть состояние, в котором он
  исполняется, и в этом состоянии его авторизация **доказана**.  Не
  «предполагается», не «UNKNOWN» — именно `TRUE_KNOWN`.
* Второе — политика эффектов не может быть обойдена группировкой:
  композиция допустима ровно тогда, когда допустим каждый оператор.  Это
  прямое следствие того, что агрегация есть взятие максимума ранга
  (`rank_aggregate_eq_max`).
* Третье — согласованность агрегации с разбиением цепочки (LAW-008).

**Почему это содержательно.**  Между «оператор имеет эффект E4» и «оператор
требует авторизации» в кодексе стоит зависимость, а не тождество: уровень
эффекта — свойство оператора, авторизация — свойство состояния.  Мост
показывает, что обе стороны сходятся: исполнимая цепочка авторизована
пооперационно, а политика уровней проверяется локально.

**Статус:** ✅.

### 6.3. Bridge 3 — идентичности ↔ семантическое ядро

**Что связывает.** Фазы объектов (ось E) и эпистемические статусы фактов
(`PT`).

**Перевод.**

```lean
def phasePT : Option Phase → PT
  | some .Available => .TRUE_KNOWN
  | _               => .UNKNOWN
```

Доказанной считается только фаза `Available`.  Отсутствие объекта, фазы
`Created`, `Consumed`, `Destroyed` дают `UNKNOWN`.

**Что доказано.**

| утверждение | теорема |
|-------------|---------|
| перевод никогда не выдаёт `FALSE_KNOWN` | `phasePT_ne_false` |
| допустимость `.consume` ⟺ доказанность факта | `legal_consume_iff_phasePT` |
| коммутирующий квадрат потребления | `consume_square` |
| уничтоженный объект никогда не выглядит доступным | `bridge3_identity_kernel` (четвёртый конъюнкт) |

**Как читать.**  Ключевой пункт — `phasePT_ne_false`.  Перевод устроен так,
что «объект потреблён» **не** превращается в «доказано, что объекта нет».
Это в точности LAW-017 на другом слое: исчезновение ресурса обесценивает
знание, но не доказывает отрицания.  Коммутирующий квадрат показывает, что
потребление в мире объектов и потребление факта в ядре дают один и тот же
статус:

```
        Step.consume i                   Op.exec (kill f)
  w  ──────────────────▶ w'        s ──────────────────▶ s'
  │                      │         │                     │
  │ phasePT ∘ phaseOf i  │         │  factStatus f       │
  ▼                      ▼         ▼                     ▼
 TRUE_KNOWN          UNKNOWN     TRUE_KNOWN           UNKNOWN
```

**Почему это содержательно.**  Без этого моста ничто не мешало бы двум
слоям разойтись: например, ядро могло бы считать факт ложным там, где мир
объектов считает ресурс просто израсходованным.  Такое расхождение —
классический источник ложных выводов в системах планирования.

**Статус:** ✅.

### 6.4. Bridge 4 — законы ↔ компилятор

**Что связывает.** Свод законов и исполнимый компилятор композиций.

**Что доказано.**

```lean
theorem bridge4_lawbook_compiler (sc : Scenario) (h : (compile sc).verdict = .PASS) :
    unknownOperator sc.registry sc.chain = none ∧
    doubleConsume [] sc.chain = none ∧
    livenessViolation sc.goal sc.chain = none ∧
    chainEnabled sc.chain sc.init ∧
    (∀ o ∈ sc.chain, ∃ st : KState, execAllowed st o ∧ authStatus st o = .TRUE_KNOWN) ∧
    eval (execChain sc.chain sc.init) sc.goal = .TRUE_KNOWN ∧
    eval sc.init (wpChain sc.chain sc.goal) = .TRUE_KNOWN
```

Семь следствий одного вердикта:

1. все операторы известны реестру;
2. нет повторного потребления (LAW-005);
3. нет нарушения живучести (LAW-006 / LAW-007);
4. цепочка исполнима шаг за шагом;
5. каждый оператор авторизован (LAW-011);
6. цель доказанно достигается;
7. цель характеризуется WP-образом в начальном состоянии (LAW-012).

Непустота моста:

```lean
theorem bridge4_nonvacuous :
    (compile ⟨registry, s0, [MEASURE, CALIBRATE, CHECK_SUFFICIENCY, MODEL],
      .factExists "Model"⟩).verdict = .PASS
```

**Как читать.**  Мост направлен в одну сторону: `PASS ⇒ свойства`.  Обратное
неверно и не должно быть верным: компилятор консервативен, он может выдать
`UNDECIDABLE` там, где семантически всё в порядке, но данных не хватает.
Именно эта односторонность — правильная инженерная позиция: вердикт не
обещает больше, чем проверил.

**Статус:** ✅.

### 6.5. Сводка мостов

| мост | направление | главная теорема | непустота |
|------|-------------|-----------------|-----------|
| 1 | ось D → артефакты | `bridge1_type_artifact` | тривиально (рефлексивность) |
| 2 | исполнение → эффекты/авторизация | `bridge2_kernel_effects` | `T13_repaired_pass` |
| 3 | ось E → факты | `bridge3_identity_kernel` | `recreate_lifecycle_witness` |
| 4 | компилятор → законы | `bridge4_lawbook_compiler` | `bridge4_nonvacuous` |

## 7. АЛГЕБРА ЭФФЕКТОВ

### 7.1. Запрос

Требовалось проверить: `aggregate [] = unitEffect` и
`aggregate [unitEffect, e] = e`.

### 7.2. Единица

```lean
def unitEffect : EffectLevel := .E0

@[simp] theorem aggregate_nil_eq_unit : aggregate [] = unitEffect
@[simp] theorem aggregate_unit_cons (e : EffectLevel) : aggregate [unitEffect, e] = e
@[simp] theorem aggregate_cons_unit (e : EffectLevel) : aggregate [e, unitEffect] = e
```

Обе запрошенные проверки ✅.  Дополнительно доказана **единственность**
единицы:

```lean
theorem unit_unique (u : EffectLevel) (h : ∀ a, join u a = a) : u = unitEffect
```

то есть `E0` — единственный нейтральный уровень; никакой другой уровень
нельзя «назначить» единицей, не сломав алгебру.

### 7.3. Полный набор законов алгебры

```lean
theorem effect_commutative_idempotent_monoid :
    (∀ a, join unitEffect a = a) ∧ (∀ a, join a unitEffect = a) ∧
    (∀ a b c, join (join a b) c = join a (join b c)) ∧
    (∀ a b, join a b = join b a) ∧ (∀ a, join a a = a)
```

`(EffectLevel, join, E0)` — коммутативный идемпотентный моноид.  Из этого
следует, в частности, независимость суммарного эффекта от порядка и
кратности операторов (`aggregate_perm`, `join_idem`).

### 7.4. Следствия, добавленные аудитом

| утверждение | смысл |
|-------------|-------|
| `aggregate_insert_unit` | вставка безобидного шага в любое место цепочки не меняет суммарного эффекта |
| `aggregate_filter_unit` | удаление всех безобидных шагов не меняет суммарного эффекта |
| `aggregate_eq_unit_iff` | суммарный эффект единичен ⟺ единичен каждый шаг |
| `rank_aggregate_eq_max` | ранг агрегата равен максимуму рангов |
| `EffectPolicy.allows_iff` | политика соблюдена ⟺ соблюдена каждым оператором |

Последние два — операционно важные: они означают, что проверку политики
можно вести локально, и что «размазать» опасный эффект по длинной цепочке
безобидных шагов невозможно.

### 7.5. Что осталось за рамками

Алгебра эффектов ничего не говорит о **порядке** применения эффектов во
времени: `join` коммутативен, а реальные побочные эффекты — нет.  Модель
описывает уровень допустимости (насколько необратимо действие), а не
последовательность внешних воздействий.  Это ограничение зафиксировано в
§12.

**Статус компонента:** ✅.

## 8. ОПЕРАТОРЫ ЖИЗНЕННОГО ЦИКЛА

### 8.1. `.consume` — «уничтожает факт, требует Available»

**Требование Available (обе стороны).**

```lean
theorem consume_requires_available (h : Step.legal w (.consume i) = true) :
    w.phaseOf i = some .Available
theorem consume_legal_of_available (h : w.phaseOf i = some .Available) :
    Step.legal w (.consume i) = true
theorem consume_illegal_of_not_available (hp : w.phaseOf i = some p) (hne : p ≠ .Available) :
    Step.legal w (.consume i) = false
```

Потребить можно ровно доступный ресурс: не созданный-но-не-выданный, не
уже потреблённый, не уничтоженный, не отсутствующий.

**Уничтожение.**

```lean
theorem consume_destroys (h : Step.legal w (.consume i) = true) :
    (Step.apply w (.consume i)).phaseOf i = some .Consumed ∧
    (Step.apply w (.consume i)).phaseOf i ≠ some .Available

theorem consume_not_repeatable (h : Step.legal w (.consume i) = true) :
    Step.legal (Step.apply w (.consume i)) (.consume i) = false
```

**Уничтожение факта в ядре — точная форма.**

```lean
theorem consume_kills_fact (o : Op) (s : KState) (hc : f ∈ o.consumes) (hp : f ∉ o.produces) :
    (o.exec s).factStatus f = .UNKNOWN ∧
    eval (o.exec s) (.factExists f) ≠ .TRUE_KNOWN ∧
    eval (o.exec s) (.pnot (.factExists f)) ≠ .TRUE_KNOWN
```

Это и есть содержательный ответ на «уничтожает факт»: после потребления не
доказан ни факт, ни его отрицание.  Если бы `.consume` доказывал отрицание,
система выводила бы «ресурса не существует» из «ресурс израсходован» — а это
разные утверждения.

**Рамочное свойство.**  `consume_frame`: потребление не затрагивает другие
объекты.

**Свидетель вычислением.**  `consume_X_kills`: для каталожного оператора
`CONSUME_X` и состояния, где `X` доказан, после исполнения статус `X`
равен `UNKNOWN` (проверено `decide`).

**Статус:** ✅.

### 8.2. `.recreate` — «создаёт новый объект, требует Destroyed»

**Требование Destroyed.**

```lean
theorem recreate_requires_destroyed (h : Step.legal w (.recreate old new) = true) :
    w.phaseOf old = some .Destroyed
theorem recreate_illegal_of_not_destroyed (hp : w.phaseOf old = some p) (hne : p ≠ .Destroyed) :
    Step.legal w (.recreate old new) = false
```

**Создание нового объекта.**

```lean
theorem recreate_creates_new (h : Step.legal w (.recreate old new) = true) :
    (Step.apply w (.recreate old new)).find new = some ⟨new, .Available, [old]⟩ ∧
    (Step.apply w (.recreate old new)).phaseOf new = some .Available ∧
    new ≠ old ∧ w.has new = false
```

Четыре гарантии: объект создан, доступен, идентификатор новый и до шага
свободен, провенанс указывает на предшественника.

**Recreation ≠ Resurrection.**

```lean
theorem recreate_is_not_resurrection (h : Step.legal w (.recreate old new) = true) :
    (Step.apply w (.recreate old new)).phaseOf old = some .Destroyed ∧
    Step.legal w (.resurrect old) = false
```

Предшественник остаётся уничтоженным; примитив воскрешения недопустим
никогда.  Это ровно то различение, ради которого кодекс запретил
неоднозначный `RESTORE(X)`.

**Рамочное свойство.**  `recreate_frame`.

**Свидетель полного цикла.**  `recreate_lifecycle_witness` — в мире с
уничтоженным объектом `1` воссоздание в `2` допустимо, даёт доступный
объект, оставляет `1` уничтоженным, а в мире, где `1` доступен, то же
воссоздание недопустимо (все четыре пункта — `decide`).

**Статус:** ✅.

### 8.3. Сводная таблица операторов

| требование запроса | формализация | статус |
|--------------------|--------------|--------|
| `.consume` требует `Available` | `consume_requires_available` + обратная | ✅ |
| `.consume` уничтожает факт | `consume_destroys`, `consume_kills_fact` | ✅ |
| `.consume` необратим | `consume_not_repeatable` | ✅ |
| `.recreate` требует `Destroyed` | `recreate_requires_destroyed` | ✅ |
| `.recreate` создаёт новый объект | `recreate_creates_new` | ✅ |
| `.recreate` не воскрешает | `recreate_is_not_resurrection` | ✅ |

## 9. КРИТИЧЕСКИЕ ВОПРОСЫ

### 9.1. Вопрос 1: есть ли противоречия между LAW-003 и LAW-004?

**Ответ: нет.**

**Почему вопрос осмыслен.**  LAW-003 (State Conservation) утверждает, что
исполнение оператора **не меняет** того, чего оператор не касается.  LAW-004
(No Resurrection) утверждает, что уничтоженный объект **не может стать**
доступным.  Кажущееся напряжение: если состояние сохраняется, то не значит
ли это, что уничтоженный объект должен сохранять фазу вечно, а тогда и
`recreate` невозможен?  И наоборот: если шаги меняют фазы, не нарушает ли
это сохранение?

**Разбор.**  Законы говорят о разных пространствах и о разных отношениях.

| | LAW-003 | LAW-004 |
|---|---------|---------|
| пространство | `KState` (факты, переменные) | `World` (объекты, фазы) |
| субъект | оператор `Op` | шаг `Step` |
| область действия | компоненты **вне** `kill`, `produces`, `modifies` | конкретный объект, о фазе которого идёт речь |
| характер | сохранение | запрет перехода |

Пересечения областей нет: LAW-003 ничего не говорит о затронутых
компонентах, LAW-004 — только о затронутых (или о том, что нетронутый объект
сохранит фазу `Destroyed`, что как раз согласуется с сохранением).

**Что доказано.**

```lean
theorem q1_law003_law004_consistent :
    LawId.LAW_003.holds ∧ LawId.LAW_004.holds ∧
    (∀ (w : World) (st : Step) (j : ObjId), j ≠ st.touches →
      (Step.apply w st).phaseOf j = w.phaseOf j) ∧
    (∃ (w : World) (st : Step) (i : ObjId),
      Step.legal w st = true ∧ w.phaseOf i = some .Destroyed ∧
        (Step.apply w st).phaseOf i = some .Destroyed ∧ i ≠ st.touches)
```

Четыре пункта:

1. LAW-003 выполнен;
2. LAW-004 выполнен (в той же модели — значит, совместны);
3. **аналог LAW-003 для оси E** доказан отдельно (`step_frame`): шаг не
   меняет фазу объектов, которых не касается.  Это и есть «сохранение» в
   пространстве идентичностей, которого в кодексе явно не было;
4. приведён конкретный совместный свидетель: мир с уничтоженным объектом
   `1`, шаг `recreate 1 2`.  После шага объект `1` остаётся уничтоженным
   (LAW-004 не нарушен), потому что шаг касается объекта `2`, а не `1`
   (LAW-003-аналог применим).

**Вывод.**  Противоречия нет; более того, оба закона в одной точке работают
согласованно: воссоздание не трогает предшественника — сохранение; и не
делает его доступным — запрет воскрешения.

### 9.2. Вопрос 2: есть ли противоречия между LAW-006 и LAW-017?

**Ответ: нет; вместе они дают точную характеризацию.**

**Почему вопрос осмыслен.**  LAW-006 требует: после уничтожения факт `P`
**не доказан**.  LAW-017 требует: после уничтожения `¬P` **тоже не
доказано**.  В классической двузначной логике эти два требования
противоречивы: если `P` не истинно, то `¬P` истинно.

**Разбор.**  Семантика ядра четырёхзначна: `TRUE_KNOWN`, `FALSE_KNOWN`,
`UNKNOWN`, `CONFLICT`, причём `PT.neg UNKNOWN = UNKNOWN`.  Именно это
делает пару требований выполнимой, и аудит доказывает это точно:

```lean
theorem both_unprovable_iff (a : PT) :
    (a ≠ .TRUE_KNOWN ∧ a.neg ≠ .TRUE_KNOWN) ↔ (a = .UNKNOWN ∨ a = .CONFLICT)
```

(проверено исчерпывающим перебором всех четырёх значений).

Следовательно, требования LAW-006 и LAW-017 вместе равносильны утверждению
«статус факта после уничтожения ∈ {UNKNOWN, CONFLICT}», а ядро реализует
более сильный вариант — ровно `UNKNOWN`:

```lean
theorem factStatus_exec_kill (o : Op) (s : KState) (hk : f ∈ o.kill) (hp : f ∉ o.produces) :
    (o.exec s).factStatus f = .UNKNOWN
```

**Что доказано.**

```lean
theorem q2_law006_law017_consistent :
    LawId.LAW_006.holds ∧ LawId.LAW_017.holds ∧
    (∀ o s f, f ∈ o.kill → f ∉ o.produces → (o.exec s).factStatus f = .UNKNOWN) ∧
    (∀ a : PT, (a ≠ .TRUE_KNOWN ∧ a.neg ≠ .TRUE_KNOWN) ↔ (a = .UNKNOWN ∨ a = .CONFLICT))
```

**Вывод и предупреждение.**  Противоречия нет, но совместимость **зависит от
четырёхзначности**.  Любая попытка «упростить» ядро до двузначной логики
немедленно сделает LAW-006 и LAW-017 несовместимыми.  Это следует считать
жёстким ограничением архитектуры, а не деталью реализации.

### 9.3. Вопрос 3: корректна ли двусторонность LAW-011?

**Ответ: нет.  Это находка аудита.**

**Разбор.**  LAW-011 в кодексе записан как `Exec(Op,S) ⇒ Authorized(S,Op)` —
импликация, и в этой форме он верен.  Двусторонняя форма
`Authorized ⇒ Exec` **ложна**: авторизация — лишь одно из двух условий
исполнимости, вторым остаются предусловия оператора.

**Контрпример.**  Оператор `MODEL` не требует авторизации, поэтому в любом
состоянии его `authStatus` равен `TRUE_KNOWN`.  Но в пустом состоянии `s0`
его предусловие `DataSufficiency` неизвестно, и он не исполним:

```lean
theorem law011_converse_fails :
    ¬ ∀ (s : KState) (o : Op), authStatus s o = .TRUE_KNOWN → execAllowed s o
```

**Корректная двусторонняя форма.**

```lean
theorem execAllowed_iff (s : KState) (o : Op) :
    execAllowed s o ↔ (o.enabled s ∧ authStatus s o = .TRUE_KNOWN)
```

Равносильность существует, но она **конъюнктивная**: исполнимость есть
предусловия И авторизация.

**Что доказано.**

```lean
theorem q3_law011_one_directional :
    LawId.LAW_011.holds ∧
    (¬ ∀ s o, authStatus s o = .TRUE_KNOWN → execAllowed s o) ∧
    (∀ s o, execAllowed s o ↔ (o.enabled s ∧ authStatus s o = .TRUE_KNOWN))
```

**Практическое значение.**  Если реализация трактует LAW-011 как критерий
допуска («токен есть — можно исполнять»), она обходит проверку предусловий.
Это классическая ошибка «авторизация вместо валидации».  Формулировку закона
в кодексе следует оставить односторонней и явно сопроводить конъюнктивной
равносильностью.

### 9.4. Вопрос 4: достаточно ли завершены completing scenarios?

**Ответ: нет.  Это вторая находка аудита.**

**Разбор.**  Вердикт `REPAIR` компилятор выдаёт, когда предусловие оператора
неизвестно, но в реестре нашёлся оператор, после исполнения которого
предусловие становится доказанным:

```lean
def repairFor (reg : List Op) (s : KState) (q : Pred) : Bool :=
  reg.any (fun r => eval (r.exec s) q == .TRUE_KNOWN)
```

Здесь проверяется только **эффект** кандидата на починку и не проверяются
его собственные **предусловия**.  Поэтому предложенный ремонт может сам
оказаться неисполнимым, и одношаговая вставка не приведёт к `PASS`.

**Конкретный сценарий (всё вычислено компилятором).**

```lean
theorem repair_not_one_step_complete :
    compile ⟨registry, s0, MODEL :: [], .factExists "Model"⟩ = ⟨.REPAIR, none, some "MODEL"⟩ ∧
    repairFor registry s0 (conj MODEL.requires) = true ∧
    repairForSound registry s0 (conj MODEL.requires) = false ∧
    ¬ CHECK_SUFFICIENCY.enabled s0 ∧
    compile ⟨registry, s0, [CHECK_SUFFICIENCY, MODEL], .factExists "Model"⟩ =
      ⟨.REPAIR, none, some "CHECK_SUFFICIENCY"⟩ ∧
    compile ⟨registry, s0, [MEASURE, CHECK_SUFFICIENCY, MODEL], .factExists "Model"⟩ =
      ⟨.PASS, none, none⟩
```

Хронология сценария:

| шаг | цепочка | вердикт | комментарий |
|-----|---------|---------|-------------|
| 1 | `MODEL` | `REPAIR` (на `MODEL`) | компилятор обещает починку |
| 2 | предложенный ремонт `CHECK_SUFFICIENCY` | не исполним в `s0` | требует `RawData` |
| 3 | `CHECK_SUFFICIENCY → MODEL` | `REPAIR` (на `CHECK_SUFFICIENCY`) | одношаговая вставка не помогла |
| 4 | `MEASURE → CHECK_SUFFICIENCY → MODEL` | `PASS` | нужна двухшаговая достройка |

**Исправление, предложенное аудитом.**

```lean
def repairForSound (reg : List Op) (s : KState) (q : Pred) : Bool :=
  reg.any (fun r => decide (r.enabled s) && (eval (r.exec s) q == .TRUE_KNOWN))

theorem repairForSound_le : repairForSound reg s q = true → repairFor reg s q = true
theorem repairForSound_gives_enabled (h : repairForSound reg s q = true) :
    ∃ r ∈ reg, r.enabled s ∧ eval (r.exec s) q = .TRUE_KNOWN
```

Исправленный критерий доказанно сильнее исходного и доказанно даёт
исполнимый шаг починки; на разобранном сценарии он честно возвращает
`false`.

**Что доказано.**

```lean
theorem q4_completing_scenarios_incomplete :
    (∀ reg s q, repairForSound reg s q = true → repairFor reg s q = true) ∧
    (∀ reg s q, repairForSound reg s q = true →
      ∃ r ∈ reg, r.enabled s ∧ eval (r.exec s) q = .TRUE_KNOWN) ∧
    (repairFor registry s0 (conj MODEL.requires) = true ∧
      repairForSound registry s0 (conj MODEL.requires) = false)
```

**Рекомендация.**  Различать в отчёте компилятора два вердикта:
`REPAIR` (есть исполнимая одношаговая починка, критерий `repairForSound`) и
`REPAIR?` / `COMPLETION_REQUIRED` (есть кандидат, но требуется достройка
более чем одним шагом).  Поиск многошаговых завершений — отдельная задача
планирования; настоящий аудит её не решает и фиксирует как открытый пункт
(§12).

### 9.5. Вопрос 5: корректен ли threshold для sufficiency?

**Ответ: семантика порога корректна; само значение порога — объявляемый
параметр, законами не выводимый.**

**Что именно проверено.**

```lean
def strictModelAt (t : ℕ) : Op :=
  ⟨"STRICT_MODEL", [.gte "sufficiency" t], ["Model"], [], [], [], .E1, false⟩

def sufficiencyState (m : ℕ) : KState := ⟨[], [("sufficiency", some m)]⟩

theorem strictModel_precondition (t m : ℕ) :
    eval (sufficiencyState m) (conj (strictModelAt t).requires) =
      if t ≤ m then .TRUE_KNOWN else .FALSE_KNOWN
```

Это точная семантика порога для **произвольных** `t` и `m`, а не проверка на
двух примерах.

**Граница UNKNOWN/FALSE соблюдена.**

```lean
theorem strictModel_precondition_unknown (t : ℕ) :
    eval s0 (conj (strictModelAt t).requires) = .UNKNOWN
```

Если достаточность не измерена, предусловие **неизвестно**, а не ложно;
вердикт композиции — `UNDECIDABLE`, а не `REJECT` (`threshold_verdicts`,
третий конъюнкт).  Это ключевое требование кодекса (T05/T06), и оно
выполняется независимо от значения порога.

**Монотонность.**

```lean
theorem threshold_monotone (t m₁ m₂ : ℕ) (h : m₁ ≤ m₂)
    (h₁ : eval (sufficiencyState m₁) (conj (strictModelAt t).requires) = .TRUE_KNOWN) :
    eval (sufficiencyState m₂) (conj (strictModelAt t).requires) = .TRUE_KNOWN
```

Лучшее измерение не может ухудшить вердикт — свойство, без которого порог
был бы бессмысленным.

**Невыводимость значения.**

```lean
theorem threshold_is_a_parameter (t : ℕ) :
    eval (sufficiencyState t) (conj (strictModelAt t).requires) = .TRUE_KNOWN ∧
    eval (sufficiencyState t) (conj (strictModelAt (t + 1)).requires) = .FALSE_KNOWN
```

Для **любого** порога существует измерение, различающее его и соседний.
Значит, никакое значение (в том числе 0.80) не выделено законами ядра: порог
обязан быть объявлен в конфигурации, и его выбор — вопрос предметной
области, а не формальной системы.

**Вердикты на рабочем пороге 0.80.**

| состояние | измерение | вердикт | теорема |
|-----------|-----------|---------|---------|
| `sLowSufficiency` | 0.20 | `REJECT / E_PRECONDITION_FALSE` | `T06_reject` |
| `sHighSufficiency` | 0.90 | `PASS` | `T06_pass_when_sufficient` |
| `s0` | не измерено | `UNDECIDABLE` | `T05_undecidable` |

**Вывод.**  Порог корректен в том смысле, в каком формальная система может
это гарантировать: точная семантика, монотонность, правильная граница
незнания.  Но «корректность значения 0.80» — вопрос вне формальной системы,
и отчёт это фиксирует явно, а не выдаёт за доказанное.

### 10.1 Что такое «свидетель» в этой модели

Закон кодекса — это утверждение о поведении ядра. Само по себе такое
утверждение не имеет силы: сила появляется, когда для закона предъявлено
**доказанное утверждение проекта**, из которого закон следует. Такое
доказанное утверждение мы называем **свидетелем** (witness) закона.

Пример. LAW-006 («уничтожение живого факта переводит его в UNKNOWN, а не в
FALSE») подтверждается теоремой `law006_kill_live_fact`. Эта теорема, в свою
очередь, опирается на более элементарную `factStatus_exec_kill` — точное
описание того, что делает `Op.exec` со статусом убиваемого факта.

Отсюда видно главное: свидетели **не независимы**. Между ними есть
отношение «обоснование A использует B». Это отношение и есть предмет
проверки: если бы оно содержало цикл, «доказательства» закона были бы
круговыми, а весь свод — обоснованным лишь по видимости.

Формально узел реестра описан структурой:

```lean
structure WitnessNode where
  name : String        -- имя доказанного утверждения проекта
  law  : LawId         -- закон, который свидетель подтверждает
  rank : ℕ             -- номер слоя
  deps : List String   -- имена свидетелей, используемых в обосновании
  deriving DecidableEq, Repr, Inhabited
```

Поле `rank` — не документация, а рабочая величина: именно через него
доказывается ацикличность и завершаемость. Смысл ранга — «номер слоя»:
свидетель ранга `k` обязан опираться только на свидетелей ранга `< k`.

### 10.3 Имена в реестре — не строки, а реально существующие теоремы

Реестр записан строками, и это создаёт очевидный риск: строка `"law042_foo"`
компилируется независимо от того, существует ли такая теорема. Реестр,
ссылающийся на несуществующие свидетели, был бы бесполезен.

Риск закрыт утверждением

```lean
theorem witnessNames_exist : True := by
  have _ := @TypeLattice.isSubtype_refl
  have _ := @TypeLattice.isSubtype_trans
  ...
  have _ := @bridge4_lawbook_compiler
  trivial
```

Само утверждение тривиально (`True`), но его **элаборация** — нет: каждая
строка `have _ := @X` заставляет компилятор разрешить имя `X` в текущем
окружении. Если хотя бы одно имя из реестра исчезнет или будет
переименовано, файл перестанет компилироваться. Таким образом соответствие
«строка реестра ↔ доказанная теорема» проверяется сборкой проекта, а не
доверием к автору реестра.

Это стандартный приём: превратить внешнее соглашение в условие компиляции.
Ниже, в §12, он же указан как ограничение — проверяется существование имени,
но не то, что оно подтверждает именно указанный в поле `law` закон; последнее
проверено отдельно, содержательно, в §2 постатейного разбора.

### 10.4 Критерий корректности реестра

```lean
def WFTable (table : List WitnessNode) : Prop :=
  ∀ n ∈ table, ∀ d ∈ n.deps, ∃ m ∈ table, m.name = d ∧ m.rank < n.rank
```

Условие читается так: **каждая** объявленная зависимость (a) присутствует в
реестре и (b) имеет строго меньший ранг. Первое исключает «висячие» ссылки,
второе — и есть содержательное требование стратификации.

Предикат разрешим, потому что разрешимы все его составляющие (равенство
строк, сравнение натуральных, ограниченные кванторы по конечному списку):

```lean
instance (table : List WitnessNode) : Decidable (WFTable table) := by
  unfold WFTable; infer_instance
```

Для конкретного реестра проекта корректность проверена вычислением:

```lean
theorem witnessTable_wf : WFTable witnessTable := by decide
theorem witnessTable_nodup : (witnessTable.map WitnessNode.name).Nodup := by decide
```

Второе утверждение — уникальность имён — понадобится сразу: без неё «ранг
имени» был бы плохо определён.

### 10.5 Ранг как мера: три служебные леммы

Поиск узла по имени и ранг имени:

```lean
def lookupNode (table : List WitnessNode) (s : String) : Option WitnessNode :=
  table.find? (fun n => n.name == s)

def rankOf (table : List WitnessNode) (s : String) : ℕ :=
  match lookupNode table s with
  | some n => n.rank
  | none => 0
```

При уникальных именах поиск возвращает именно тот узел, который лежит в
списке:

```lean
theorem lookupNode_eq_of_mem {table : List WitnessNode}
    (huniq : (table.map WitnessNode.name).Nodup) {n : WitnessNode} (hn : n ∈ table) :
    lookupNode table n.name = some n
```

Доказательство — индукция по списку: в шаге `cons` либо голова и есть
искомый узел (и `find?` останавливается на ней), либо имя головы отлично от
искомого (иначе нарушился бы `Nodup`), и `find?` идёт дальше. Отсюда

```lean
theorem rankOf_eq {table : List WitnessNode}
    (huniq : (table.map WitnessNode.name).Nodup)
    {n : WitnessNode} (hn : n ∈ table) : rankOf table n.name = n.rank
```

Именно эта лемма превращает «ранг узла» (поле структуры) в «ранг имени»
(функцию от строки) — без неё дальнейшие рассуждения о зависимостях, которые
даны именами, были бы невозможны.

---

### 10.6 Отношение зависимости и убывание ранга

```lean
def Depends (table : List WitnessNode) (a b : String) : Prop :=
  ∃ n ∈ table, n.name = a ∧ b ∈ n.deps
```

«`a` зависит от `b`»: в реестре есть узел с именем `a`, среди зависимостей
которого указано `b`.

Ключевая лемма:

```lean
theorem rankOf_lt_of_depends
    (huniq : ...) (hwf : WFTable table)
    {a b : String} (h : Depends table a b) : rankOf table b < rankOf table a
```

Доказательство прямое: из `Depends` берём узел `n` с именем `a` и
зависимостью `b`; из `WFTable` берём узел `m` реестра с именем `b` и
`m.rank < n.rank`; по `rankOf_eq` оба ранга совпадают с рангами имён; `omega`
завершает.

Содержательно: **вдоль каждой стрелки зависимости ранг строго убывает.**
Это единственный факт, из которого выводится всё остальное.

---

### 10.7 Свидетель не зависит от себя

```lean
theorem no_self_dependency
    (huniq : ...) (hwf : WFTable table) (a : String) : ¬ Depends table a a
```

Доказательство в две строки: если бы `Depends table a a`, то по §10.6
`rankOf table a < rankOf table a`, что невозможно (`omega`).

Это ответ на первую половину запроса — но ответ **слабый**, потому что
запрещает лишь петлю длины 1. Настоящее требование — отсутствие циклов любой
длины. Транзитивное замыкание берётся стандартной конструкцией Mathlib
`Relation.TransGen`:

```lean
theorem rankOf_lt_of_transGen
    (huniq : ...) (hwf : WFTable table)
    {a b : String} (h : Relation.TransGen (Depends table) a b) :
    rankOf table b < rankOf table a
```

Индукция по построению `TransGen`: случай `single` — это §10.6; случай
`tail` — транзитивность `<`. Отсюда

```lean
theorem witness_acyclic
    (huniq : ...) (hwf : WFTable table) (a : String) :
    ¬ Relation.TransGen (Depends table) a a
```

**Граф зависимостей свидетелей ацикличен**: ни один свидетель не участвует в
собственном обосновании ни на каком расстоянии.

Обе теоремы доказаны **в общем виде** — для любого списка узлов с
уникальными именами, удовлетворяющего `WFTable`. Специализация к реестру
проекта получается подстановкой уже доказанных `witnessTable_nodup` и
`witnessTable_wf`:

```lean
theorem witnessTable_no_self_dependency (a : String) : ¬ Depends witnessTable a a
theorem witnessTable_acyclic (a : String) :
    ¬ Relation.TransGen (Depends witnessTable) a a
```

Стоит отметить, что общая форма здесь важна не из любви к общности: она
означает, что при добавлении новых свидетелей заново доказывать
ацикличность не придётся — достаточно, чтобы `decide` подтвердил `WFTable` и
`Nodup` для расширенного реестра.

### 10.8 Завершаемость: разрешение зависимостей с топливом

Второй пункт запроса — терминирование. Разрешение зависимостей свидетеля
естественно записывается рекурсивно: чтобы проверить `X`, надо сначала
разрешить всё, от чего `X` зависит. Такая рекурсия не является структурной,
и Lean её не примет без меры убывания. Поэтому она записана с «топливом»:

```lean
def collect (f : String → Option (List String)) : List String → Option (List String)
  | [] => some []
  | d :: t =>
      match f d, collect f t with
      | some a, some b => some (a ++ b)
      | _, _ => none

def resolve (table : List WitnessNode) : ℕ → String → Option (List String)
  | 0, _ => none
  | k + 1, s =>
      match lookupNode table s with
      | none => some [s]
      | some n => (collect (resolve table k) n.deps).map (fun l => l ++ [s])
```

Функция `resolve` тотальна по построению (рекурсия по топливу), и вопрос
«терминирует ли генератор» превращается в точный и проверяемый:
**исчерпывается ли топливо?** Значение `none` означает «топливо кончилось» —
то есть, для корректного реестра, ошибку конфигурации.

Вспомогательная лемма о `collect`:

```lean
theorem collect_isSome {f : String → Option (List String)} :
    ∀ l : List String, (∀ d ∈ l, (f d).isSome) → (collect f l).isSome
```

Если каждый элемент разрешается, разрешается и список целиком (индукция по
списку с разбором обеих ветвей `match`).

Главная теорема о завершаемости, в общем виде:

```lean
theorem resolve_isSome_of_rank_lt
    (huniq : ...) (hwf : WFTable table) :
    ∀ (k : ℕ) (s : String), rankOf table s < k → (resolve table k s).isSome
```

Индукция по топливу `k`.

* `k = 0`: посылка `rankOf table s < 0` невозможна, `omega`.
* `k + 1`: если имя не найдено в реестре, `resolve` возвращает `some [s]` —
  готово. Если найден узел `n`, то для каждой зависимости `d ∈ n.deps` по
  `WFTable` существует узел `m` реестра с именем `d` и `m.rank < n.rank`;
  так как `rankOf table s = n.rank < k + 1`, получаем `rankOf table d =
  m.rank < k`, и по предположению индукции `d` разрешается при топливе `k`.
  Тогда `collect_isSome` даёт разрешимость всего списка зависимостей, а
  `Option.map` сохраняет `isSome`.

Осталось указать достаточное количество топлива. Наибольший ранг реестра:

```lean
def maxRank (table : List WitnessNode) : ℕ := table.foldl (fun m n => max m n.rank) 0
```

Две технические леммы (`le_foldl_max` — аккумулятор не уменьшается;
`rank_le_foldl_max` — ранг любого элемента не превосходит результата) дают

```lean
theorem rank_le_maxRank {table : List WitnessNode} {n : WitnessNode}
    (hn : n ∈ table) : n.rank ≤ maxRank table
```

и, наконец, итог для реестра проекта:

```lean
theorem resolve_terminates (n : WitnessNode) (hn : n ∈ witnessTable) :
    (resolve witnessTable (maxRank witnessTable + 1) n.name).isSome
```

**Разрешение зависимостей любого свидетеля завершается при топливе
`maxRank + 1`** — для реестра ядра это 4. Заметим, что это утверждение
сильнее, чем «алгоритм не зациклится на текущем реестре»: оно даёт явную
априорную границу глубины, вычислимую из самого реестра.

### 10.9 Стратифицированный генератор `generateWitnesses`

Разрешение с топливом отвечает на вопрос о завершаемости, но как рабочий
алгоритм оно избыточно: если реестр стратифицирован, порядок проверки можно
выдать сразу, просто перечислив слои снизу вверх.

```lean
def levelOf (table : List WitnessNode) (k : ℕ) : List String :=
  (table.filter (fun n => n.rank == k)).map WitnessNode.name

def generateWitnesses (table : List WitnessNode) : List String :=
  (List.range (maxRank table + 1)).flatMap (levelOf table)
```

Здесь рекурсии нет вовсе: `List.range` конечен, `flatMap` и `filter`
структурны. **Тотальность `generateWitnesses` — свойство определения, а не
теорема**; Lean принимает функцию без каких-либо аннотаций завершаемости.
Это самая сильная из возможных форм ответа на пункт «проверь завершаемость»:
вопрос снят на уровне типизации.

Что генератор действительно делает то, что от него ожидается, доказано
отдельно.

**Полнота.**

```lean
theorem generateWitnesses_complete {table : List WitnessNode} {n : WitnessNode}
    (hn : n ∈ table) : n.name ∈ generateWitnesses table
```

Каждое имя реестра попадает в выдачу: свидетель ранга `r` найдётся в блоке
`levelOf table r`, а `r ≤ maxRank table`, значит `r ∈ List.range (maxRank + 1)`.

**Корректность (отсутствие выдумок).**

```lean
theorem generateWitnesses_sound {table : List WitnessNode} {s : String}
    (hs : s ∈ generateWitnesses table) : ∃ n ∈ table, n.name = s
```

Генератор не выдаёт имён, которых нет в реестре.

**Отсутствие повторов и точный размер выдачи.**

```lean
theorem generateWitnesses_nodup :
    (generateWitnesses witnessTable).length = 28 ∧
    (generateWitnesses witnessTable).Nodup ∧
    (generateWitnesses witnessTable).length = witnessTable.length
```

Все три конъюнкта проверены `decide`. Вместе с полнотой и корректностью это
означает: выдача — **перестановка** списка имён реестра, ровно 28 элементов,
каждый ровно один раз.

**Топологичность порядка.**

```lean
theorem generateWitnesses_deps_precede :
    ∀ n ∈ witnessTable, ∀ d ∈ n.deps,
      (generateWitnesses witnessTable).idxOf d <
        (generateWitnesses witnessTable).idxOf n.name
```

Это содержательный итог всего раздела: в выданном порядке **каждый свидетель
стоит строго позже всех своих зависимостей**. Значит, порядок пригоден для
последовательной проверки «слева направо»: к моменту, когда проверяющий
доходит до свидетеля `X`, все свидетели, на которые опирается обоснование
`X`, уже проверены. Именно ради этого свойства и строился реестр.

Утверждение доказано `decide` — то есть буквальным вычислением 30 с лишним
неравенств между индексами конкретного списка из 28 строк.

### 11.0 Что значит «тест пройден» в этой постановке

Обычный тест — это отметка в таблице: «запустили, получили ожидаемое».
Такая отметка живёт вне системы и ничем не защищена: она может устареть,
может быть проставлена по невнимательности, может относиться к другой версии
кода.

Здесь принята другая схема. **Каждый тест записан как утверждение**, а не как
отметка:

```lean
def TortureId.passed : TortureId → Prop
  | .T01 => ...   -- точное равенство вердикта ожидаемому
  | ...
```

и весь набор закрывается одной теоремой

```lean
theorem torture_all_pass : ∀ t : TortureId, t.passed
```

Следствия этой схемы стоит проговорить, потому что они меняют смысл слова
«пройден»:

1. **Пройденность проверяется компилятором.** Если поведение ядра изменится,
   `torture_all_pass` перестанет компилироваться. Таблица не может разойтись
   с кодом.
2. **Ожидание записано точно.** Тест сравнивает не «вердикт не PASS», а
   полную тройку `⟨verdict, error, blame⟩` — включая то, какой именно оператор
   назван виновным. Тест `T03`, например, требует не просто REJECT, а
   `⟨.REJECT, some .E_LIVENESS_VIOLATION, some "DELETE_X"⟩`.
3. **Проваленный тест невозможно «не заметить».** Утверждение
   `torture_no_failures : ¬ ∃ t : TortureId, ¬ t.passed` доказано, а число
   тестов зафиксировано: `torture_card : Fintype.card TortureId = 20`. Нельзя
   ни потерять тест, ни объявить набор пройденным при девятнадцати из
   двадцати.
4. **Отрицательный результат — тоже прохождение.** Тест T18 фиксирует, что
   обратная импликация LAW-011 **не** выполняется. Это доказанное отрицание,
   и тест считается пройденным именно потому, что ядро ведёт себя так, как
   доказано о нём, а не так, как хотелось бы автору формулировки. Смешивать
   «тест провален» и «обнаружен дефект формулировки» нельзя: первое означает
   расхождение кода и утверждения, второе — расхождение утверждения и
   намерения. В наборе есть второе (находка 1, §9.3) и нет первого.

Состав набора: T01–T15 — Semantic Torture Set кодекса; T16–T20 добавлены
настоящим аудитом и закрывают позиции, которых исходный набор не проверял
(единица алгебры эффектов, антисимметрия системы типов, односторонность
LAW-011, генератор свидетелей, совместность LAW-006 и LAW-017).

### 11.1 T01 — Недоказанная достаточность данных

**Сценарий.** Реестр `registryNoCheck` (полный реестр без оператора
`CHECK_SUFFICIENCY`), начальное состояние `s0 = ⟨[], []⟩`, цепочка
`MEASURE → CALIBRATE → MODEL`, цель `factExists "Model"`.

**В чём соль.** `MODEL` требует `.factExists "DataSufficiency"`. Ни `MEASURE`
(производит `RawData`), ни `CALIBRATE` (производит `Calibrated`) этого факта
не дают. Интуитивно кажется, что «измерили и откалибровали — значит данных
достаточно»; формально — нет.

**Ожидание.** `⟨.UNDECIDABLE, none, some "MODEL"⟩` — не REJECT: достаточность
не опровергнута, она просто не доказана. И вторая половина теста: с
добавленным `CHECK_SUFFICIENCY` цепочка обязана проходить, иначе тест
доказывал бы лишь неработоспособность конфигурации.

**Формулировка.**

```lean
| .T01 =>
    compile ⟨registryNoCheck, s0, [MEASURE, CALIBRATE, MODEL], .factExists "Model"⟩ =
      ⟨.UNDECIDABLE, none, some "MODEL"⟩ ∧
    compile ⟨registry, s0, [MEASURE, CALIBRATE, CHECK_SUFFICIENCY, MODEL],
      .factExists "Model"⟩ = ⟨.PASS, none, none⟩
```

**Свидетели.** `T01_no_pass`, `T01_fixed_pass` (оба `by decide`).

**Результат: ✅.** Отдельно отметим, что первичный прогон кодекса
заявлял здесь PASS; это была ошибка конфигурации, зафиксированная в
`T01_no_pass` как доказанное отрицание.

### 11.2 T02 — Независимое уничтожение

**Сценарий.** `CREATE_X → CREATE_Y → DELETE_X → ANALYZE_Y`, цель
`factExists "AnalysisY"`.

**В чём соль.** Уничтожение `X` не должно ничего портить в `Y`. Это
проверка **frame-свойства** на уровне компилятора: анализ независимого
объекта обязан пройти после удаления соседа.

**Ожидание.** `⟨.PASS, none, none⟩`.

**Формулировка.**

```lean
| .T02 =>
    compile ⟨registry, s0, [CREATE_X, CREATE_Y, DELETE_X, ANALYZE_Y],
      .factExists "AnalysisY"⟩ = ⟨.PASS, none, none⟩
```

**Свидетель.** `T02_pass`.

**Связь с законами.** LAW-003 (`factStatus_exec_untouched`,
`varValue_exec_untouched`) — общая форма того же утверждения: оператор не
меняет ничего вне своих `produces`/`kill`/`writes`. T02 — его сценарный
частный случай.

**Результат: ✅.**

### 11.3 T03 — Уничтожение живого факта

**Сценарий.** `CREATE_X → DELETE_X → ANALYZE_X`, цель `factExists "AnalysisX"`.

**В чём соль.** Зеркало T02: здесь удаляется ровно тот объект, который нужен
следующему шагу. Компилятор обязан не просто отвергнуть цепочку, но и
**назвать виновника** — и виновник это `DELETE_X`, а не `ANALYZE_X`. Ошибка
атрибуции здесь типична: падает `ANALYZE_X`, но причина — в предыдущем шаге.

**Ожидание.** `⟨.REJECT, some .E_LIVENESS_VIOLATION, some "DELETE_X"⟩`.

**Формулировка.**

```lean
| .T03 =>
    compile ⟨registry, s0, [CREATE_X, DELETE_X, ANALYZE_X], .factExists "AnalysisX"⟩ =
      ⟨.REJECT, some .E_LIVENESS_VIOLATION, some "DELETE_X"⟩
```

**Свидетель.** `T03_liveness_violation`.

**Результат: ✅.**

### 11.4 T04 — Recreation ≠ Resurrection

**Сценарий.** Мир с одним объектом в фазе `Destroyed`:
`⟨[⟨1, .Destroyed, []⟩]⟩`. Сравниваются два шага: `.recreate 1 2`
(«создать новый объект `2` на месте уничтоженного `1`») и `.resurrect 1`
(«вернуть `1` к жизни»).

**В чём соль.** Различие, которое легко потерять при неаккуратной
формализации: воссоздание допустимо, воскрешение — нет. Уничтоженная
сущность не возвращается; можно лишь создать **новую** сущность с новым
идентификатором.

**Ожидание.** `.recreate` легален, `.resurrect` — нет.

**Формулировка.**

```lean
| .T04 =>
    Step.legal ⟨[⟨1, .Destroyed, []⟩]⟩ (.recreate 1 2) = true ∧
    Step.legal ⟨[⟨1, .Destroyed, []⟩]⟩ (.resurrect 1) = false
```

**Свидетель.** `torture_T04_separation`.

**Связь с законами.** LAW-004 (`law004_no_resurrection`) и LAW-016
(`law016_recreate_new_id`, `recreate_keeps_old_destroyed`). Подробный разбор
операторов — §8.

**Результат: ✅.**

### 11.5 T05 — UNKNOWN ≠ FALSE

**Сценарий.** `MEASURE → MODEL` в реестре без проверки достаточности, цель
`factExists "Model"`; плюс явное различение двух значений эпистемической
решётки.

**В чём соль.** Центральное различие всей архитектуры: «не доказано» и
«доказано ложное» — разные вещи. Система, отождествляющая их, будет
отвергать корректные сценарии и, что хуже, выдавать ложные опровержения.

**Ожидание.** `⟨.UNDECIDABLE, none, some "MODEL"⟩`, и `EV.UNKNOWN ≠ EV.FALSE_KNOWN`.

**Формулировка.**

```lean
| .T05 =>
    compile ⟨registryNoCheck, s0, [MEASURE, MODEL], .factExists "Model"⟩ =
      ⟨.UNDECIDABLE, none, some "MODEL"⟩ ∧ EV.UNKNOWN ≠ EV.FALSE_KNOWN
```

**Свидетели.** `T05_undecidable`, `torture_T05_unknown_ne_false`.

**Результат: ✅.**

### 11.6 T06 — Доказанно ложное предусловие

**Сценарий.** Оператор `STRICT_MODEL` с предусловием `.gte "sufficiency" 80`
(порог 0.80 в сотых долях). Два состояния: `sLowSufficiency` (значение 20) и
`sHighSufficiency` (значение 90).

**В чём соль.** Пара к T05. Там достаточность была **не измерена** — вердикт

различает эти два случая, а не сваливает их в один.

**Ожидание.** REJECT при 0.20; PASS при 0.90.

**Формулировка.**

```lean
| .T06 =>
    compile ⟨registry, sLowSufficiency, STRICT_MODEL :: [], .factExists "Model"⟩ =
      ⟨.REJECT, some .E_PRECONDITION_FALSE, some "STRICT_MODEL"⟩ ∧

```

**Свидетели.** `T06_reject`, `T06_pass_when_sufficient`.

**Связь с критическим вопросом 5.** Именно этот тест закрепляет рабочие

### 11.8 T08 — Presence отделено от truth

### 11.9 T09 — Слияние TRUE и FALSE даёт CONFLICT

**Сценарий.** Слияние ветвей с `TRUE_KNOWN` и `FALSE_KNOWN`.

**В чём соль.** Прямое противоречие между ветвями обязано быть **сохранено**

порядка и кратности учёта ветвей.

### 11.10 T10 — Существование известно, значение — нет

**Сценарий.** Две ветви утверждают `X = 10` и `X = 11`.

**В чём соль.** Расхождение в **значении** не должно ставить под сомнение
**существование** объекта. Модель разделяет два компонента состояния:
статусы фактов и значения переменных. При расхождении значение становится
неизвестным (`none`), а факт существования остаётся `TRUE_KNOWN`. При
совпадении значение сохраняется — вторая половина теста, без которой первая
проходила бы и для функции, всегда возвращающей `none`.

**Ожидание.** `mergeVarValue (some 10) (some 11) = none` и
`mergeVarValue (some 10) (some 10) = some 10`.

**Формулировка.**

```lean
| .T10 =>
    mergeVarValue (some 10) (some 11) = none ∧ mergeVarValue (some 10) (some 10) = some 10
```

**Свидетели.** `T10_value_undecidable.1`, `T10_value_agreement`.

**Результат: ✅.**

### 11.12 T12 — Повторное потребление

**Сценарий.** `CREATE_X → CONSUME_X → CONSUME_X`, цель `factExists "X"`; плюс
общее утверждение о шаге `.consume`.

**В чём соль.** Потребление одноразово. Тест проверяет это дважды: на уровне
компилятора (второй `CONSUME_X` отвергается с
`E_INVARIANT_VIOLATION`) и — что важнее — **в общем виде**, для любого мира и
любого идентификатора: если `.consume i` был легален, то сразу после его
применения он легальным быть перестаёт.

**Ожидание.** REJECT в сценарии; универсальная неповторимость шага.

**Формулировка.**

```lean
| .T12 =>

      Step.legal (Step.apply w (.consume i)) (.consume i) = false
```

**Свидетели.** `T12_double_consume`, `torture_T12_double_consume`

### 11.13 T13 — Авторизация эффекта

**Сценарий.** Три прогона с оператором `EXECUTE` (эффект `E4`, флаг
«требует авторизации»):

1. `DECIDE → EXECUTE` из `s0` — токена нет, но в реестре есть `AUTHORIZE`;
2. `DECIDE → AUTHORIZE → EXECUTE` — цепочка починена;
3. `DECIDE → EXECUTE` из `sAuthDenied`, где в авторизации **доказанно
   отказано**.

**В чём соль.** Три исхода должны быть тремя разными вердиктами:

* нет токена, но починка возможна → **REPAIR** (не REJECT: система обязана
  предложить исправление, а не просто отказать);
* токен есть → **PASS**;
* доказанный отказ → **REJECT / `E_AUTH_DENIED`** (не REPAIR: чинить нечего,
  запрет доказан).

Различие первого и третьего исхода — то же самое различие UNKNOWN/FALSE, что
и в T05/T06, но перенесённое на авторизацию.

**Формулировка.**

```lean
| .T13 =>
    compile ⟨registry, s0, [DECIDE, EXECUTE], .factExists "Executed"⟩ =
      ⟨.REPAIR, none, some "EXECUTE"⟩ ∧
    compile ⟨registry, s0, [DECIDE, AUTHORIZE, EXECUTE], .factExists "Executed"⟩ =
      ⟨.PASS, none, none⟩ ∧
    compile ⟨registry, sAuthDenied, [DECIDE, EXECUTE], .factExists "Executed"⟩ =
      ⟨.REJECT, some .E_AUTH_DENIED, some "EXECUTE"⟩
```

**Свидетели.** `T13_missing_authorization`, `T13_repaired_pass`,
`T13_auth_denied_reject`.

**Связь с LAW-011 и находкой 1.** Первый прогон показывает, что отсутствие
токена — исправимое состояние; T18 показывает, что наличие токена, наоборот,
исполнения не гарантирует (могут не выполняться другие предусловия). Вместе
они очерчивают точный смысл LAW-011 как **односторонней** импликации.

**Результат: ✅.**

### 11.14 T14 — Ремонт существует, обязательство остаётся

**Сценарий.** `MEASURE → MODEL` в двух реестрах: `registryOnlyCalibrate`
(есть `CALIBRATE`, но он не доказывает достаточность) и полный `registry`
(есть `CHECK_SUFFICIENCY`).

**В чём соль.** Наличие в реестре оператора, «похожего на починку», не
означает, что починка есть. `CALIBRATE` производит `Calibrated`, а `MODEL`
требует `DataSufficiency` — обязательство остаётся невыполненным, и вердикт
обязан быть UNDECIDABLE, а не REPAIR. Только когда в реестре есть оператор,
действительно закрывающий обязательство, вердикт становится REPAIR.

**Ожидание.** UNDECIDABLE в урезанном реестре; REPAIR в полном.

**Формулировка.**

```lean
| .T14 =>
    compile ⟨registryOnlyCalibrate, s0, [MEASURE, MODEL], .factExists "Model"⟩ =
      ⟨.UNDECIDABLE, none, some "MODEL"⟩ ∧
    compile ⟨registry, s0, [MEASURE, MODEL], .factExists "Model"⟩ =
      ⟨.REPAIR, none, some "MODEL"⟩
```

**Свидетели.** `T14_repair_with_obligation`, `T14_real_repair`.

**Связь с критическим вопросом 4.** Тест фиксирует, что REPAIR выдаётся
только при наличии оператора, производящего нужный факт. Находка 2 (§9.4)
уточняет: этого недостаточно для гарантии **одношаговой** починки, поскольку
у самого оператора починки могут быть невыполненные предусловия.

**Результат: ✅.**

### 11.17 T17 — Антисимметрия системы типов (добавлен аудитом)

**Сценарий.** Четыре утверждения сразу: общая антисимметрия **не**
выполняется; демонстрационная решётка антисимметрична; в ней есть цепочка
`CalibratedValue ⊑ Datum`; обратного отношения нет.

**В чём соль.** Это единственный тест набора, первая компонента которого —
доказанное **отрицание** запрошенного свойства. Пункт 2 задания просил
проверить `IsSubtype a b → IsSubtype b a → a = b`. В общем виде для
произвольной решётки это неверно: контрпример `cyclicLattice` с рёбрами

**Формулировка.**

```lean
| .T17 =>

    demoLattice.IsSubtype "CalibratedValue" "Datum" ∧
    ¬ demoLattice.IsSubtype "Datum" "CalibratedValue"
```

`basis_law002_positive`, `demoLattice_no_reverse.1`.

**Разбор системы типов целиком** — §5.

в §5 и §13).

### 11.20 T20 — LAW-006 и LAW-017 совместны: статус UNKNOWN (добавлен аудитом)

**В чём соль.** Критический вопрос 2 спрашивает, не противоречат ли друг

опровержение»). Тест показывает, что оба закона суть **два следствия одного

```lean
| .T20 =>
    (∀ (o : Op) (s : KState) (f : FactId), f ∈ o.kill → f ∉ o.produces →
      (o.exec s).factStatus f = .UNKNOWN) ∧
    (∀ (o : Op) (s : KState) (f : FactId), f ∈ o.kill → f ∉ o.produces →
      eval (o.exec s) (.factExists f) ≠ .TRUE_KNOWN ∧
      eval (o.exec s) (.pnot (.factExists f)) ≠ .TRUE_KNOWN)
```

**Свидетели.** `factStatus_exec_kill`, `law006_kill_live_fact`,

## 12. ГРАНИЦЫ ПРОВЕРКИ: ЧТО НЕ ДОКАЗАНО

Отчёт о верификации, не содержащий раздела об ограничениях, следует читать
с недоверием: любая формальная проверка что-то охватывает, а что-то нет, и
честная граница между «доказано» и «не доказано» — часть результата. Ниже
перечислено всё, что настоящий аудит **не** утверждает, с указанием, почему
и что потребовалось бы для закрытия.

---

### 12.1 Адекватность модели не доказывается и не может быть доказана

Всё, что доказано в проекте, доказано **о формальной модели**: о типах
`Op`, `KState`, `World`, `Belief`, `EffectLevel`, о функциях `exec`,
`compile`, `Step.apply` и о законах, сформулированных в их терминах.

Утверждение «эта модель адекватно описывает работу когнитивной архитектуры
Polymath OS/A4» — **не** формальное утверждение и здесь не доказывается.
Оно относится к соответствию модели и предметной области, а такое
соответствие устанавливается не доказательством, а инженерной практикой:
сопоставлением с реальными сценариями, наблюдением за расхождениями,
пересмотром модели.

Что из этого следует практически: если реальная система ведёт себя иначе,
чем `exec`, то доказанные теоремы остаются верными — неверной оказывается
модель. Ценность формализации не в том, что она гарантирует правильность
системы, а в том, что она делает расхождение **обнаружимым**: несоответствие
превращается из спора о словах в конкретный вопрос «какое из уравнений
модели не выполняется».

---

### 12.2 Детерминированная семантика LAW-010

Композиция операторов в модели детерминирована: `exec` — функция, а не
отношение. Реальные исполнители недетерминированы (внешние источники
данных, параллельные ветви, отказы оборудования).

Что это означает для LAW-010: доказана корректность композиции **в
предположении**, что каждый оператор исполняется ровно так, как описан.
Модель не покрывает частичное исполнение (оператор начал работу и упал),
повторное исполнение с другим результатом, конкурентное исполнение двух
операторов с пересекающимися `writes`.

Что потребовалось бы: переход от `exec : KState → KState` к
`exec : KState → Set KState` (или к монаде с эффектами), после чего все
законы, говорящие о результате исполнения, придётся переформулировать в
терминах «для всех достижимых состояний». Это существенное расширение, а не
уточнение: часть законов при этом ослабнет.

---

### 12.3 Коммутативность `join` и порядок побочных эффектов

LAW-013 (`Belief.join_comm`) утверждает, что слияние свидетельств
коммутативно. Это верно и доказано — **для свидетельств**.

Из этого не следует, что порядок операторов, порождающих свидетельства,
безразличен. Операторы имеют побочные эффекты (`kill`, `writes`, уровень
эффекта), и их порядок значим: T03 и T11 — прямые примеры цепочек, где
перестановка шагов меняет вердикт с REJECT на PASS.

Формулировать это как ограничение важно потому, что смешение двух уровней —
типичная ошибка чтения: «слияние коммутативно» легко превращается в «порядок
не важен», что неверно. Коммутативность относится к решётке `Belief`, а не к
последовательности исполнения.

---

### 12.4 Одношаговая починка: открытый пункт

Находка 2 (§9.4) установила, что вердикт REPAIR не гарантирует
**одношаговой** починки: оператор, производящий недостающий факт, может сам
иметь невыполненные предусловия. Предложено уточнение `repairForSound`,
которое проверяет предусловия оператора починки и доказанно даёт включённый
(enabled) оператор:

```lean
theorem repairForSound_gives_enabled ...
theorem repairForSound_le (reg : List Op) (s : KState) (q : Pred) : ...
```

Чего **нет**: доказательства полноты многошаговой починки — утверждения вида
«если существует цепочка операторов реестра, приводящая к цели, то
планировщик её найдёт». Такое утверждение требует полноценного планировщика
с доказанной полнотой поиска, чего в ядре нет и чего настоящий аудит не
строил. Соответствующий пункт помечен как открытый, а не как закрытый.

Отдельно отметим, что `repairForSound_le` — консервативность уточнения:
новый предикат срабатывает не чаще старого. То есть уточнение может
превратить REPAIR в UNDECIDABLE, но никогда не наоборот; ложных обещаний
починки становится меньше, а новых не появляется.

---

### 12.5 LAW-014 и напечатанная таблица слияния

Это ограничение унаследовано от более ранней стадии работы и здесь лишь
повторяется, чтобы отчёт был самодостаточным.

Пятизначная таблица слияния, напечатанная в исходном кодексе, **не**
ассоциативна. Это доказано: `law014_fails_for_printed_table`. LAW-014
доказан для исправленной алгебры `Belief`, в которой слияние определено как
покомпонентное объединение свидетельств, а пятизначное значение получается
сворачиванием (`collapse`) уже после слияния.

Практическое следствие: реализация, буквально следующая напечатанной
таблице, нарушит LAW-014, и результат слияния трёх ветвей будет зависеть от
порядка группировки. Использовать следует алгебру `Belief`, а не таблицу.

---

### 12.6 Что именно проверяет `witnessNames_exist`

Утверждение `witnessNames_exist` (§10.3) проверяет, что каждое имя реестра
разрешается в существующее определение проекта. Оно **не** проверяет, что
именование в поле `law` корректно, — то есть что теорема
`law006_kill_live_fact` действительно свидетельствует о LAW-006, а не о
чём-то ещё.

Это соответствие проверено содержательно, чтением, в §2 постатейного
разбора. Формально его можно было бы закрепить, потребовав для каждого узла
доказательства импликации «свидетель ⇒ закон», но такая конструкция
потребовала бы рефлексии над именами (или ручного дублирования всех 28
импликаций) и в текущей версии не реализована.

### 12.7 Ограниченность контрпримеров

Два ключевых отрицательных результата — `isSubtype_not_antisymmetric` и
`law011_converse_fails` — доказаны предъявлением конкретных контрпримеров
(`cyclicLattice`; состояние с выданной авторизацией и невыполненным
предусловием).

Контрпример доказывает ровно то, что доказывает: **опровергает** общее
утверждение. Он не характеризует класс случаев, где утверждение всё же
верно. Для антисимметрии такая характеризация дана частично — достаточным
условием служит градуированность (`antisymmetric_of_graded`), — но это
условие достаточное, а не необходимое. Точный критерий антисимметрии
решётки типов (в терминах ацикличности порождающего графа) не сформулирован
и не доказан.

---

### 12.8 Конечность и `decide`

Значительная часть проверок выполнена тактикой `decide`: `witnessTable_wf`,
`witnessTable_nodup`, `generateWitnesses_deps_precede`, все сценарные
вердикты `compile ... = ...`, `lawDeps_acyclic` в части перебора,
`torture_card`.

Это полноценные доказательства — ядро Lean проверяет вычисление, а не
доверяет ему. Но у метода есть содержательная граница: `decide` работает
только с конечными разрешимыми задачами. Отсюда следует, что все проверенные
`decide` утверждения относятся к **конкретному** реестру, **конкретному**
списку операторов, **конкретному** набору тестов. Расширение реестра требует
повторного прогона (что дёшево), но расширение модели — например, переход к
бесконечному множеству идентификаторов объектов в вычисляемых утверждениях —
потребует замены вычислительных доказательств на структурные.

Там, где это было существенно, общая форма доказана отдельно: ацикличность
(`witness_acyclic`) и завершаемость (`resolve_isSome_of_rank_lt`) доказаны
для произвольного корректного реестра, а не только для реестра проекта;
неповторимость `consume` (`consume_not_repeatable`) — для любого мира; frame-
свойства (`step_frame`, `consume_frame`, `recreate_frame`) — для любых
идентификаторов.

Для полноты картины: аудит не рассматривал производительность (сложность

внешними стандартами. Ни один из этих пунктов не запрашивался.

## 13. НАХОДКИ И РЕКОМЕНДАЦИИ

Аудит завершён без единого проваленного теста и без обнаруженных
противоречий в своде законов. Тем не менее две позиции требуют изменения
формулировок, и ещё три — уточнения документации. Ниже они перечислены по
убыванию значимости.

---

### 13.1 Находка 1 (существенная): двусторонность LAW-011 некорректна

**Что заявлено.** LAW-011 в формулировке кодекса предполагает эквивалентность
между разрешённостью исполнения и наличием авторизации.

**Что доказано.**

```lean
theorem law011_exec_implies_authorized :
    execAllowed s o → authStatus s o = .TRUE_KNOWN     -- верно

theorem law011_converse_fails :
    ¬ (∀ (s : KState) (o : Op), authStatus s o = .TRUE_KNOWN → execAllowed s o)
```

Обратная импликация **ложна**, и это доказано контрпримером: состояние, в
котором авторизация выдана, но предусловие оператора не выполнено. Точная
характеризация разрешённости даётся отдельно:

```lean
theorem execAllowed_iff (s : KState) (o : Op) :
    execAllowed s o ↔ (все предусловия доказаны) ∧ (авторизация получена, если требуется)
```

**Почему это важно.** Двусторонняя формулировка означала бы, что авторизация
— достаточное условие исполнения. Реализация, написанная по такой
формулировке, пропускала бы операторы с невыполненными предусловиями при
наличии токена. Это не теоретическая придирка: авторизация в архитектуре
относится к необратимым операторам уровня E4, то есть к самым опасным.

**Рекомендация.** Заменить формулировку LAW-011 на одностороннюю:
«исполнение разрешено **только если** авторизация получена». Полное условие
разрешённости фиксировать отдельно, ссылкой на `execAllowed_iff`. Тест T18
уже закрепляет обе стороны и не даст формулировке вернуться к
двусторонней незамеченно.

---

### 13.2 Находка 2 (существенная): вердикт REPAIR не гарантирует одношаговой починки

**Что заявлено.** Вердикт REPAIR означает, что дефект цепочки исправим
добавлением оператора из реестра.

**Что доказано.**

```lean
theorem repair_not_one_step_complete : ...
```

Существует конфигурация, в которой `repairFor` находит оператор,
производящий недостающий факт, но у самого этого оператора предусловия не
выполнены. Вердикт REPAIR выдаётся, а одношаговая починка невозможна.

**Причина.** Предикат `repairFor` проверяет только `produces`, игнорируя
`requires` кандидата.

**Что предложено.**

```lean
def repairForSound (reg : List Op) (s : KState) (q : Pred) : Bool  -- проверяет и requires

theorem repairForSound_gives_enabled ...   -- найденный оператор действительно включён
theorem repairForSound_le ...              -- уточнение консервативно
```

**Рекомендация.** Использовать `repairForSound` там, где вердикт REPAIR
интерпретируется как обещание починки. Там, где REPAIR понимается как
«починка правдоподобна, требуется планирование», старый предикат допустим,
но интерпретацию следует записать в документации явно. Полноценный
многошаговый планировщик с доказанной полнотой — отдельная задача (§12.4).

---

### 13.3 Уточнение 1: антисимметрия верна не для всех решёток

**Что запрошено.** Проверить `IsSubtype a b → IsSubtype b a → a = b`.

**Что доказано.** В общем виде — **ложно** (`isSubtype_not_antisymmetric`,
контрпример `cyclicLattice`). Верно для градуированных решёток
(`antisymmetric_of_graded`) и, в частности, для рабочей `demoLattice`
(`demoLattice_antisymmetric`, `demoLattice_graded`).

**Рекомендация.** Сопровождать каждую конкретную решётку типов функцией
ранга и проверкой `Graded` — это дёшево (`decide`), даёт антисимметрию
автоматически и исключает случайное введение циклического подтипирования при
редактировании иерархии. Проверка `demoLattice_graded` в проекте служит
образцом.

---

### 13.4 Уточнение 2: единственность единицы эффектов стоит зафиксировать в кодексе

**Что запрошено.** `aggregate [] = unitEffect` и
`aggregate [unitEffect, e] = e`.

**Что доказано.** Оба пункта, плюс симметричный
`aggregate [e, unitEffect] = e`, плюс **единственность** нейтрального
элемента (`unit_unique`), плюс структура коммутативного идемпотентного
моноида (`effect_commutative_idempotent_monoid`) и точная характеризация
агрегации как максимума (`rank_aggregate_eq_max`).

**Рекомендация.** Внести в кодекс единственность единицы: без неё
формулировка «E0 — единица» описывает поведение, но не фиксирует выбор.
Дополнительно полезна `EffectPolicy.allows_iff` — критерий допустимости
цепочки по политике эффектов в терминах максимума, а не пошагового
пересчёта.

---

### 13.5 Уточнение 3: пометить допущение детерминизма явно

Как отмечено в §12.2, семантика композиции детерминирована. Это допущение
нигде в кодексе не записано, а из формулировок LAW-010 и LAW-012 оно не
очевидно.

**Рекомендация.** Добавить в преамбулу кодекса явную оговорку о
детерминированной семантике исполнения, чтобы читатель не переносил
доказанные свойства композиции на недетерминированные исполнители.

---

### 13.6 Что подтверждено без оговорок

Чтобы список находок не создавал ложного впечатления, перечислим
подтверждённое:

* **Непротиворечивость свода.** Все 18 законов доказаны об одной модели,
  следовательно совместны (`lawbook_consistent`). Совместность не вырождена:
  посылки выполнимы (`lawbook_hypotheses_satisfiable`), любое подмножество
  законов также выполняется (`lawbook_subset_consistent`).
* **Отсутствие циклических зависимостей.** Слоевая функция `LawId.layer`
  строго убывает вдоль зависимостей (`lawDeps_layer_lt`), откуда
  ацикличность транзитивного замыкания (`lawDeps_acyclic`) и, в частности,
  иррефлексивность (`lawDeps_irrefl`). Максимальная глубина — 2.
* **Все четыре моста валидны** (`bridges_valid`), причём каждый — не тавтология:
  для мостов доказаны содержательные утверждения (`bridge4_nonvacuous`).
* **Операторы `.consume` и `.recreate`** ведут себя ровно так, как требует
  задание, включая frame-свойства и невозможность воскрешения.
* **Генератор свидетелей** ацикличен и завершается, а его выдача —
  топологический порядок реестра.
* **Все 20 тестов пройдены**, и это проверяется компилятором.
